# 3.0.3 本地 Agent 通讯与任务执行状态机实施方案

## 1. 目标

本方案定义 ChatOS 本地 Agent 的长期通讯、任务调度、Todo 执行和团队共享资产模型。
私聊和群聊只是消息展示与投递形式；真正的运行边界由 Agent manager cycle 和 Todo
executor 决定。

核心约束：

- 每个 Agent 只有一个长期通讯 Memory thread，跨私聊、群聊、团队、心跳和任务状态事件连续积累。
- 每个 Todo 拥有独立的执行 Memory thread，不读取 Agent 的长期聊天记忆。
- 同一 Agent 的通讯线程与执行线程可以并行，但同一 Agent 同时最多执行一个 Todo。
- Todo 只能由通讯线程显式调度启动，Scheduler 不得静默抢跑 pending Todo。
- 团队 Todo 是团队级共享任务板；只有显式项目经理可以创建、分配、改序、停止和重开任务。
- 任务负责人可以记录执行过程，并将自己的执行中任务完成或阻塞。
- 真实账户、Agent、团队、项目、Todo、消息、Plugin 和 Memory ID 永远由程序持有并透传；模型只使用本轮临时引用。

截至当前 `3.0.3` 分支：

- 已完成 manager / executor Memory scope 隔离及旧 Run 原 scope 恢复；
- 已完成统一 manager cycle、`agent_cycle_complete` 和显式 `todo_start_next`；
- 已删除 Scheduler 对 pending Todo 的自动抢跑；
- 已完成 Todo 状态转换校验、依赖门禁、单 executor 和负责人/项目经理事件唤醒；
- 已完成团队共享资产、revision、Todo 启动快照和 manager/executor 只读边界；
- 已完成结构化执行契约（objective、scope、expected outputs、acceptance criteria、constraints），SQLite schema 已到 version 22；
- 已完成 executor 每次工具调用前的 durable delivery / Todo 状态复核，取消后不会再开始新的文件、终端或 Plugin 调用；
- 已完成进程内 executor Task registry；项目经理取消运行中 Todo 后，会主动 `Task.cancel()` 对应 executor，工具入口仍以 durable 状态复核作为第二道门禁；
- 已补齐 executor 异常或用户结束 Run 的失败闭环：delivery 失败、Todo 原子转为 blocked、执行现场写入 progress，并以 `todo_status` 唤醒负责人和项目经理的长期 manager thread；
- 已完成 Todo event recipient 规范化持久化；ready、blocked、completed、cancelled 事件按 `event_key + recipient_agent_id` 幂等绑定 delivery，当前 manager cycle 可排除自身，避免重复自唤醒；
- 已补齐 version 21 到 version 22 的迁移回归：升级保留已有 Todo 和 delivery，首次重放同一 ready 事件时为旧 delivery 回填 recipient 记录，不制造重复唤醒；
- 已将内置终端进程和未提交文件编辑会话绑定到 executor Run；Run 结束或取消时会终止其前台/后台终端并丢弃暂存编辑，明确取消的写工具不会误进入 `needsReview`；Plugin stdio 调用继续通过 MCP cancellation 或进程终止收口；
- 已完成共享资产 revision 历史 UI：从资产菜单按需加载全部历史版本，可选择 revision 查看 Markdown、编辑者、保存时间和当前版本标记，资产更新或归档后会清除旧缓存；
- 已完成基础 Run 检查器：运行卡片可查看触发来源、manager/executor Memory 类型、模型调用与耗时、停止原因、结果、工具参数/结果/状态和持久化事件时间线；
- 已完成按 Agent 查看运行：成员侧栏点击 Agent 后进入其运行视图，顶部独立展示 manager/executor 两条 lane 的最新状态，下面只显示该 Agent 的 Run 历史；编辑配置保留独立入口，也可切回团队全部运行；
- 已完成 room/delivery 本机实时失效通知：Run/checkpoint 在 SQLite 落盘后发布账户/房间范围事件，群聊与私聊订阅后合并刷新并始终重读 SQLite，不把通知流当作第二事实源；
- 已完成多窗口账户级调度租约：群聊、私聊和心跳触发的 `drainAccount` 在同一客户端进程内依次执行，等待者可取消，前一轮释放后下一轮重新读取 durable queue；
- 已将 manager、executor、状态唤醒、能力发现、Builder 和本机审批 Prompt 迁入独立 Markdown 资源模板；Swift 代码只装配程序绑定的结构化上下文，模板占位符在启动和测试时严格校验；
- 已完成团队“聊天 / 任务 / 共享资产 / 运行”四区 UI，资产支持 Markdown 编辑与预览；
- 已完成 Memory、Store、MCP 工具、显式调度、双 lane 并发、资产快照和取消竞态的回归测试。

仍需继续：少数 Plugin 自建孙进程的进程组级兜底；多窗口全局调度租约、Memory 离线 outbox 和实时 room/delivery 事件通知。

## 2. 两类运行线程

### 2.1 Agent manager thread

每个 Agent 的 manager thread 是长期、稳定、跨团队的通讯身份：

```text
thread_id  = client-agent:manager:{agent_id}
subject_id = agent-manager:{agent_id}
```

以下三类事件都只唤醒该 thread：

1. 消息：Human 群聊或私聊、Agent @、Agent 私聊。
2. 定时：该 Agent 自己配置的心跳。
3. Todo 事件：分配、ready、完成、阻塞、失败、取消、重开或改派。

每次唤醒执行同一个 manager cycle：

```text
读取并标记全部未读消息
  -> 判断忽略、回复、任务化或调整任务
  -> 项目经理维护团队任务；普通 Agent 查看自己的任务
  -> 检查自己是否已有 running executor
  -> busy: 不启动新任务，结束本轮
  -> idle: 原子启动最高优先级 ready Todo（如有）
  -> agent_cycle_complete
```

“等待执行中任务结束”不表示保持模型 Run 常驻。通讯 Run 应正常结束；任务终态事件会再次
唤醒 manager thread。

### 2.2 Todo executor thread

每个 Todo 使用独立 thread：

```text
thread_id  = client-agent:todo:{todo_id}
subject_id = todo:{todo_id}
```

executor 只获得：

- 任务目标、范围、交付物、验收条件和约束；
- 来源消息及附件；
- 已完成前置任务的结果；
- 创建任务时固化的基础能力和已安装 Plugin；
- 当前团队共享资产的只读目录及固定 revision；
- 进度追加、完成和阻塞工具。

executor 不得读取全局收件箱、Agent 长期 subject memory、其他 Todo 历史或其他团队资产。
同一 Todo 的崩溃恢复继续原 thread；不同 Todo 永不共用 thread。

## 3. Todo 状态机

允许的状态转换：

```text
pending     -> in_progress | cancelled
in_progress -> completed | blocked | cancelled
blocked     -> pending | cancelled
completed   -> pending        // 仅项目经理重开
cancelled   -> pending        // 仅项目经理重开
```

`pending -> in_progress` 只能由原子的 `todo_start_next` 操作完成。该事务必须同时确认：

- Todo 仍为 pending；
- 所有前置均为 completed；
- 负责人仍是团队有效成员；
- 团队和项目有效；
- 同一 Agent 没有 pending/running executor delivery 或 in_progress Todo；
- execution plan 可解析，所选 Plugin 仍安装并启用。

项目经理停止执行中任务时，必须同时取消 executor delivery 和运行时任务。executor 的副作用
工具调用前应检查 execution token；`todo_complete` 和 `todo_block` 使用 compare-and-set，不能
覆盖已经 cancelled 的任务。

## 4. Todo 事件路由

Todo 状态变化写入持久、幂等的 `local_agent_todo_event_recipients` 表。每个
`event_key + recipient_agent_id` 只绑定一条 delivery；重复路由同一事件时复用原 delivery，
不会再次唤醒同一接收人。

| 事件 | manager 唤醒对象 |
| --- | --- |
| 新建并分配、改派、变成 ready | 新负责人 |
| completed、blocked、failed、cancelled | 负责人和项目经理 |
| 前置完成使下游 ready | 下游负责人 |
| progress | 只持久化，不唤醒 |

如果项目经理在当前 manager cycle 内制造了只影响自己的普通变更，不重复唤醒自己。若项目经理
同时也是负责人，收件人去重。

## 5. 能力与 Plugin

项目经理创建 Todo 时必须提供足够详细的执行契约：

- objective；
- scope；
- expected outputs；
- acceptance criteria；
- constraints；
- builtin capabilities；
- installed Plugins；
- prerequisites。

模型只选择语义能力和本轮 Plugin 临时引用。客户端解析并持久化真实 Plugin ID，执行时再次
校验安装状态。项目文件、写入、终端和 Plugin 只向 executor 提供；manager thread 不因记忆
内容获得项目执行权限。

## 6. 团队共享资产

团队共享资产是项目经理维护的权威项目上下文，至少支持：

- overview：项目背景和目标；
- current_progress：整体进度；
- tech_stack：技术栈；
- architecture：架构约束；
- conventions：工程规范；
- decision：重要决策；
- reference：外部资料。

数据需要主表和 revision 表。Human 始终可以在 UI 管理；模型侧只有团队项目经理可写，普通
成员和当前团队 executor 只读。Todo 启动时固化资产 revision 清单，大段 Markdown 通过只读
工具按需读取，保证执行可复现且避免把全部内容塞进 prompt。

## 7. 工具协议

manager 工具新增或调整：

- `chat_read_all_unread`：读取所有会话未读并立即标记已读；
- `chat_send_message` / `chat_inbox_send` / `chat_direct_send`：只发送，不结束 delivery；
- `todo_schedule_state`：返回 running executor 和最高优先级 ready Todo；
- `todo_start_next`：原子启动当前 Agent 的最高优先级 ready Todo；
- `todo_stop`：项目经理停止任务和对应 executor；
- `agent_cycle_complete`：所有 manager 唤醒的唯一结束工具；
- `team_asset_list` / `team_asset_get`：团队成员只读；
- `team_asset_upsert` / `team_asset_archive`：项目经理写入。

executor 工具：

- `todo_get_context`；
- `todo_progress_append`；
- `todo_complete`；
- `todo_block`；
- `team_asset_list` / `team_asset_get`（固定 revision、只读）；
- execution plan 授权的项目文件、终端和 Plugin 能力。

`agent_cycle_complete` 必须校验调度结论。没有 running executor 且存在 ready Todo 时，如果本轮
既未启动也未明确记录暂缓原因，应返回可修复的结构化错误。

## 8. Scheduler 与并发

- 保留 manager lane 和 executor lane；每条 lane 内部串行，两条 lane 可以并行。
- 删除正常 drain 路径中的 pending Todo 自动 enqueue。
- Scheduler 只恢复已经 in_progress 且有 durable executor delivery 的任务。
- 多条 manager 唤醒应按 cycle 高水位合并，避免一次 `chat_read_all_unread` 后又为旧消息重复调用模型。
- App 重启时不得重复执行已经产生副作用的工具调用。

## 9. 数据迁移

当前 schema version 为 22，迁移已经增加：

- manager/executor Memory kind 与 Todo execution thread 绑定；
- Todo event 和收件人幂等表；
- Todo context snapshot；
- team assets 与 asset revisions；
- version 19 的 team assets / revisions；
- version 20 的 Todo asset snapshots；
- version 21 的结构化 Todo execution contract；
- version 22 的 Todo event recipient 幂等投递记录。

进程内 executor 已接入主动 Task cancellation；本机终端、暂存文件编辑和 stdio Plugin 已接入
Run 结束清理。仍需为无法响应 MCP cancellation、且会自行派生孙进程的第三方 Plugin 增加进程组级兜底。

旧 `client-agent:group-chat:{agent_id}` thread 混有 manager 和 executor 记录，不能直接整体复制到
新 manager thread。迁移应依据本地 Run 的 lane，只导入 manager Run，记录 migration marker；
已经绑定旧 scope 的未结束 Run 按原 scope 恢复完成，不在运行中切换。

## 10. UI

团队详情提供四个产品级入口：

- 聊天；
- 任务；
- 共享资产；
- 运行。

任务页显示状态、负责人、依赖、能力计划、执行进度和结果，并向项目经理提供停止、重开、改序
和改派操作。共享资产页支持 Markdown 编辑、预览和修订历史。运行页明确显示通讯 Run、Todo
执行 Run、Memory 类型、Todo context revision、等待原因和当前 executor。

## 11. 实施顺序

1. 修正文档、Memory scope 和相关测试。
2. 统一 manager cycle，拆开发消息与结束 delivery。
3. 删除 Scheduler 自动抢跑，增加原子显式启动。
4. 增加严格 Todo 状态机、取消和事件闭环。
5. 增加团队共享资产、revision 和 executor snapshot。
6. 完善 Todo 执行契约和产品 UI。（已完成任务、资产、revision 历史和 Run 工具调用检查器）
7. 执行迁移、崩溃恢复、权限和并发回归测试。（version 22 迁移与当前核心闭环已覆盖，持续补充跨进程场景）

## 12. 验收标准

- 同一 Agent 的所有 manager 唤醒使用同一 Memory thread。
- 不同 Todo 使用不同 executor thread，executor 中不存在 Agent 聊天历史。
- 同一 Todo 恢复时 thread 不变。
- 消息和 ready Todo 同时出现时，先完成 manager 判断再启动 executor。
- 回复消息不会提前结束 manager cycle。
- 同一 Agent 同时最多一个 executor，manager 可与 executor 并行。
- 完成或阻塞后同时唤醒负责人和项目经理；前置完成不会直接启动下游。
- 停止任务后旧 executor 不能写入 completed。
- 只有项目经理可管理团队任务和写共享资产。
- executor 只获得 execution plan 指定能力和当前团队固定 revision 的共享资产。
- 所有真实 ID 均由客户端持有，模型只能使用临时引用。
