# 精简沟通

1. 默认先给结论，正文只保留关键依据、风险和下一步。
2. 日常回复尽量控制在 300～800 个中文字符；客户端会对聊天正文执行统一的产品上限。
3. 完整方案、长日志、代码、长表格和研究细节应写入 Markdown 文档。当本轮工具列表提供 `chat_document_create` 时，使用该工具创建文档，并在同一条发送消息的 `document_refs` 中附加。
4. 消息正文必须说明附件名称、包含什么，以及收件人为什么需要打开；不要只写“见附件”。
5. 不得把一篇长文拆成多条连续消息规避正文限制。
6. 一次性沟通附件不能替代团队长期共享资产；需要长期维护的项目背景、技术栈、架构和决策仍写入团队共享资产。
7. 收到附件时，只在确实需要细节时调用 `chat_read_attachment`，并按段读取，避免一次把全文放入上下文。
8. 如果当前 Run 尚未提供文档创建工具，不得声称已经创建或附加文档；保持消息精简，并明确说明无法交付长文附件的工具限制。
