- 已完成每个 Agent/room 独立的稳定未读游标，以及招募、移出成员、创建项目/团队提案的 Human 确认闭环；
- 已完成 Agent 独立 `agent_project:{agent_id}:{project_id}` Memory scope；

## 1. 目标

3.0.3 在 ChatOS macOS 客户端内实现独立的多 Agent 群聊功能。每个团队必须绑定一个用户主动选择的本地项目，但 Agent 群聊不是项目工作区的默认页签，也不会为所有项目自动创建。群聊、消息、投递、运行调度和插件调用均在本机完成，不依赖 Codex CLI、Cloud Agent、Task Runner 或服务端编排。

服务端只承担可选的联网能力：

- Memory Engine 的召回、摘要和持久化；
- 账号、模型配置、插件目录及插件安装包分发。

已经安装到客户端的插件在 Agent 运行期间由本机 Plugin Runtime 直接启动和调用，不经过服务端中转。

## 2. 产品边界

项目是团队的必选工作边界，不引入公司、组织、员工账户或服务端团队模型。产品入口独立于项目导航；项目只有在用户显式创建团队时才进入这套系统。

```text
Local Project
  └── Explicitly Created Agent Team / Room
        ├── Human
        ├── Agent A + private memory
        ├── Agent B + private memory
        ├── Agent Builder + controlled creation tools
        └── shared local transcript
```

第一阶段只实现：

- 从独立的 Agent 群聊入口选择项目并创建团队；
- 一个被选择的项目最多创建一个活跃 Agent 团队；
- 添加已有 Agent 或手动创建 Agent；
- 通过内置 Agent Builder 生成 Agent 草案，用户确认后创建并加入群聊；
- 用户通过 `@Agent` 唤醒一个或多个 Agent；
- 未 `@` 时交给群聊默认 Agent；
- Agent 可以通过群聊工具读取消息、回复并 `@` 其他 Agent；
- 每个 Agent 独立 Memory；
- Agent 可以调用客户端已安装插件；
- Agent profile 可由 Human 单独授予“招募和解雇成员”以及“查看本地项目并创建团队”权限；
- 本地 checkpoint、取消、重试和崩溃恢复；
- 对自动互相唤醒设置明确预算。

第一阶段不实现：

- 公司与组织架构；
- 服务端群聊或服务端 Agent 调度；
- 独立任务系统和排期系统；
- 跨设备同步；
- App 完全退出后的后台执行；
- 自动 Git worktree 和自动合并。

## 3. 核心原则

### 3.1 群聊不是 Memory

群聊记录是本地 SQLite 中的共享事实源。Memory 是各 Agent 独立的长期认知，不用聊天记录替代，也不把整段群聊自动复制进长期 Memory。

MVP 使用以下 Memory scope：

```text
agent:{agent_id}
agent_project:{agent_id}:{project_id}
```

运行上下文固定绑定 `agent_id` 和 `project_id`。模型不能通过工具参数指定身份，因此 Agent A 无法读取或写入 Agent B 的 Memory。

Memory Engine 不可用时：

- 群聊和本地运行仍可继续；
- 使用最近一次成功召回的本地缓存；
- 待同步记录写入本地 outbox；
- 网络恢复后补传。

### 3.2 本地 Relay MCP 是协作内核

参考 `ai_chat` / Relay 的核心不是复刻聊天页面，而是让所有 Agent 通过同一个 MCP 协作。ChatOS 在客户端内维护一个账户级 `LocalAgentRelayMCPServer`；Human UI、delivery queue 和每个独立 Agent Run 都围绕同一份本地团队与消息事实源工作。

```text
Human UI
   └── local team/message store
            ↑
Local Relay MCP ── Agent A (own runtime + own memory + allowed plugins)
                ├─ Agent B (own runtime + own memory + allowed plugins)
                └─ Agent C (own runtime + own memory + allowed plugins)
```

Scheduler 只负责根据持久化 delivery 唤醒 Agent，不直接替 Agent 读取群聊或拼接完整上下文。Agent 被唤醒时只获得轻量触发 envelope，不自动注入完整聊天历史：

```json
{
  "room_id": "room-id",
  "delivery_id": "delivery-id",
  "trigger_message_id": "message-id",
  "reason": "mentioned"
}
```

Agent 连接本地 Relay MCP 后，通过以下工具按需获取和发送信息：

```text
relay_bootstrap
chat_list_members
chat_read_unread
chat_read_messages
chat_mark_read
agent_propose_member
chat_send_message
```

由于 Agent 本身就在 ChatOS 客户端内运行，第一版 MCP transport 是进程内连接：`LocalAgentRelayMCPServer.connect` 为当前 Agent Run 产生身份绑定的 MCP session，再把 tool definitions/outcomes 交给 `ChatOSAgentRuntime`。这不是由 Scheduler 临时拼装的普通工具集合；所有 Agent 都连接同一个 MCP 服务和同一个持久化协作域。未来需要支持外部 Agent 时，只需在该 Server 外增加 stdio/Streamable HTTP adapter，无需重写聊天、权限、投递或幂等逻辑。

每条 MCP session 固定绑定 `owner_user_id + project_id + room_id + agent_id + delivery_id`。这些身份不能通过工具参数切换，避免 Agent 冒充其他成员或跨项目读取消息。

Agent 的回复必须通过 `chat.send_message` 落库。本轮 Runtime 的 `completionCheck` 以 delivery 是否产生回复为准，防止模型文本未持久化或重试产生重复消息。

### 3.3 本地插件直接执行

新增 `LocalAgentToolBroker` 抽象，并由 `NativePluginToolBroker` 实现。实现复用现有：

- `NativePluginManifestLoader`；
- `NativePluginStdioClient`；
- `NativePluginRuntimeStore`；
- 工具权限与审批策略；
- Artifact 注册；
- Browser/Computer Use 可视会话与独占执行。

远程 Plugin Relay 与本地 Agent 共用执行内核：

```text
Remote Relay -> signature verification -> NativePluginToolBroker
Local Relay MCP Agent -> identity-bound local run scope -> NativePluginToolBroker
```

本地 Agent 不伪造服务端签名，也不绕过权限、审批和审计。

## 4. 本地领域模型

### 4.1 Agent profile

```text
LocalAgentProfile
- id
- ownerUserID
- name
- description
- rolePrompt
- modelConfigID
- defaultPluginIDs
- defaultSkillIDs
- status
- createdAtUnixMs
- updatedAtUnixMs
```

Agent profile 可复用于多个项目。项目内权限和职责放在 room member 上，避免把项目路径或权限写进全局身份。

### 4.2 Room 与成员

```text
ProjectAgentRoom
- id
- ownerUserID
- projectID
- name
- goal
- defaultAgentID?
- status
- createdAtUnixMs
- updatedAtUnixMs

ProjectAgentRoomMember
- roomID
- agentID
- role
- responsibility
- pluginAllowlist
- status
- joinedAtUnixMs
```

MVP 对同一项目只允许一个 active room。

### 4.3 消息与投递

```text
ProjectAgentMessage
- id
- roomID
- senderKind       // human | agent | system
- senderID
- content
- replyToMessageID?
- sourceRunID?
- causationID?
- createdAtUnixMs

ProjectAgentDelivery
- id
- roomID
- messageID
- targetAgentID
- triggerKind      // mention | default_agent | agent_mention
- status           // pending | running | completed | failed | cancelled
- attempt
- hopCount
- deduplicationKey
- claimedAtUnixMs?
- completedAtUnixMs?
- createdAtUnixMs
```

每个 Agent 在每个 room 还维护一条独立的 `ProjectAgentReadCursor`。游标不是纯时间戳，
而是 `(created_at_unix_ms, message_id)`，因此同一毫秒内产生多条消息也不会漏读；游标只允许
向前推进，Agent 自己发送的消息不会进入自己的 unread。`chat_read_unread` 返回稳定分页结果，
处理完成后由 Agent 显式调用 `chat_mark_read`。`chat_send_message` 成功时会尽力确认当前触发消息，
但消息和后续 delivery 的事务提交不依赖这次游标更新。

投递由唯一 `deduplicationKey` 保证幂等。同一个 Agent 对同一条消息最多拥有一个有效 delivery。

### 4.4 运行记录

`LocalAgentRun` 保存：

- delivery、room、project 和 agent 的不可变绑定；
- `AgentRunCheckpoint`；
- policy 与模型配置快照；
- 工具清单摘要；
-状态、错误和时间戳。

工具调用 receipt 继续由 `AgentRunCheckpoint` 管理，副作用调用结果不确定时进入人工确认，不能自动重放。

## 5. 本地调度

`LocalAgentGroupChatCoordinator` 负责消息路由和运行触发。`LocalAgentScheduler` 负责执行并发：

- 同一个 Agent 串行；
- 不同 Agent 可并行；
- 同一 delivery 只能被一个 worker claim；
- App 重启后将遗留的 running delivery 恢复为待检查或 pending；
- 用户可以暂停本轮、取消单个 Agent 或停止全部 Agent。

Agent 互相唤醒限制：

```text
maximumHopCount = 4
maximumAgentRunsPerRootMessage = 12
sameAgentPerMessage = 1
```

超过预算时写入一条 system message，并等待用户继续，不自动扩展预算。

## 6. Agent Builder

Agent Builder 是客户端内置 profile，只能使用受控配置工具：

```text
project.inspect
model.list
plugin.list_installed
agent.draft
agent.create
agent.update
room.add_member
```

Builder 首先返回结构化 `LocalAgentDraft`。创建前由客户端展示确认卡片。可授予权限必须是项目权限、用户已授权插件权限和 Builder 工具策略的交集。Builder 不能创建另一个拥有 Agent 创建能力的普通 Agent。

没有人员权限的 room Agent 不能创建或移出成员。获得 `agent.staff.hire` 与
`agent.staff.terminate` 的 Agent，才会在当前 running delivery 的身份绑定 MCP session 中看到
`agent_propose_member` 和 `agent_propose_member_removal`。工具用 MCP tool call id 作为幂等
request key，只写入 pending proposal；
账户、项目、room、提案者和 source delivery 均来自不可变 session，不接受模型参数覆盖。Human
确认时客户端会重新读取当前可用模型与本机已安装 Plugin，并在一个 SQLite transaction 中完成
Agent profile 创建、room 加入、默认 Agent 补位和 proposal resolve。移出成员只影响当前项目
团队，保留可复用 profile、独立 Memory 与其他团队关系。拒绝只改变 proposal 状态。

获得 `local.project.list` 的 Agent 才会看到统一的 `team_propose`。它的 `project_option` 是客户端
动态生成的单选项：现有项目只向模型展示名称和本轮临时 token，真实 `project_id` 不进入 Prompt、
tool schema、tool result 或 `relay_bootstrap`。客户端在进程内把 token 映射回真实 ID，写入提案，
Human 确认时必须原样透传，不能按名称反查或由模型覆盖。选择“新建项目”时，Agent 只提供名称、
说明、团队名称与目标；确认后 ChatOS 在默认授权工作区创建目录和项目，再用程序生成的 ID 绑定团队。

## 7. 客户端 UI

左侧资源栏在“AI 创作”下方增加独立一级入口“Agent 群聊”。项目工作区仍只保留项目目录、用户消息和项目设置。

```text
应用
AI 创作
Agent 群聊
本机终端
```

进入后先看到已创建的团队/会话列表；点击“创建团队”时必须选择一个尚未绑定团队的项目。创建动作不会修改其他项目，也不会为其他项目初始化群聊数据。

当前入口默认落在“Agent 管理”，而不是自动打开第一个团队。Agent profile 是账户在本机的可复用资产：

- 查看所有已创建 Agent；
- 所有 Agent 都通过同一个创建/编辑流程，不存在“管家”类型；
- 可勾选“允许招募和解雇成员”和“允许查看本地项目并创建团队”两项独立高风险权限；
- 统一调整模型、角色 Prompt 和默认本机 Plugin；
- 将已有 Agent 加入一个或多个项目团队；
- 进入具体团队后再设置该 Agent 在当前项目中的角色、职责和 Plugin allowlist。

群聊页面包含：

- 消息流与回复关系；
- `@` 成员选择器；
- Agent 工作中、等待审批、失败和已停止状态；
- 可折叠工具调用记录与 Artifact；
- 成员侧栏；
- 添加已有 Agent、手动创建、让 Agent Builder 创建；
- 暂停本轮和停止全部 Agent。

## 10. 第一阶段验收标准

- 数据只写本地 SQLite；
- 同一项目无法创建两个 active room；
- 非 room 成员不能作为消息发送者或 delivery 目标；
- `@Agent` 使用稳定 Agent ID 解析，重名时不误投递；
- 重复路由不会产生重复 delivery；
- 同一个 Agent 只能 claim 一个活动 delivery；
- message、delivery 和状态变更在事务中提交；
- 删除/归档项目不会让 Agent 读取其他项目的数据；
- 测试不依赖网络、服务端或 Codex CLI。

## 11. `3.0.3` 当前实施状态

截至当前分支，以下链路已经落地：

```text
项目群聊消息（SQLite）
  → 本地 delivery queue / claim
  → LocalAgentGroupChatScheduler
  → AgentRuntime
  → 用户模型配置对应的模型 API
  → Local Relay MCP: relay_bootstrap / chat_read_unread / chat_mark_read / chat_send_message
  → 回复和后续 @Agent delivery 写回 SQLite
```

已完成：

- `LocalAgentGroupChatRun` 与完整 `AgentRunCheckpoint` 的 SQLite 持久化；
- Run 身份固定绑定账户、项目、房间、Agent、delivery 和 root message；
- `LocalAgentRelayMCPServer` 是所有本地 Agent 的共享协作 MCP；每次连接都固定当前 Agent、项目、团队和 delivery 身份；
- `relay_bootstrap` 一次返回当前 Agent 身份、团队、成员目录和唤醒消息；本地项目 ID 不返回模型；
- `relay_bootstrap` 同时返回当前 Agent 的 unread 首页；消息历史和 unread 都使用 `(created_at_unix_ms, message_id)` 稳定游标分页；
- 每个 Agent/room 有独立只前进的已读游标；`chat_mark_read` 不能修改其他 Agent 的状态，自己发送的消息不计入自己的 unread；
- `AgentToolProviderRegistry` 合并 Relay MCP session 和本地插件工具，并拒绝工具名覆盖；
- 本地 Scheduler 消费项目成员队列，不通过服务端选择 Agent 或路由消息；
- Scheduler 每轮先原子 claim 每个 Agent 最多一条 delivery，再让不同 Agent 的 AgentRuntime 并行执行；同一 Agent 必须等待本轮完成后才会领取下一条 delivery；
- 首次 Prompt 只携带 delivery envelope，不注入完整群聊记录；
- 每个 Agent 使用 `agent_project:{agent_id}:{project_id}` 独立 Memory subject；
- Memory Engine 暂时不可用时，新 delivery 仍可无 Memory 执行，并在 Run event 中明确记录；
- Agent 回复中使用稳定 Agent ID 的 mention 会在本地继续产生和消费下一跳 delivery；
- Agent profile 可显式选择本机已安装 Plugin；客户端直接启动其 stdio MCP，复用现有权限、审批、Artifact 和视觉会话运行时，不经过服务端 Relay 调度；
- 已完成内置 Agent Builder：通过受控的项目/模型/本机 Plugin 快照生成 `LocalAgentDraft`，先展示客户端确认卡片，用户确认后才创建并加入群聊；
- Builder 规划阶段不暴露创建或成员管理写工具，确认阶段由客户端重新读取模型与 Plugin allowlist，防止过期草案或模型参数越权；
- 只有显式获得人员管理权限的 Agent 才能通过 `agent_propose_member` 或 `agent_propose_member_removal` 提交 pending 提案；Human 在群聊中的提案卡片确认后才会原子创建/加入或移出当前团队；
- 已增加独立 Agent 管理首页；Agent profile 可跨团队复用，并可在管理页修改模型、Prompt 和默认本机 Plugin，再通过“加入团队”进入项目群聊；
- Agent 管理页使用统一创建入口；人员管理与本地项目/团队权限是 profile 上的显式权限，不通过名称、Prompt 或特殊 Agent 类型判断；
- `team_propose` 把已有项目与“新建项目”合并为单选参数。模型只看到显示名和临时 token；真实项目 ID 由客户端内部映射、持久化并在确认时透传。新项目固定创建在 ChatOS 默认授权工作区，Agent 不能提交任意路径；
- 手动创建 Agent 已改用可用模型选择器，不再要求用户手输模型配置 ID；
- 成员侧栏可编辑 Agent profile 与当前项目成员配置；名称、角色、职责、Prompt、模型和本机 Plugin allowlist 在同一个 SQLite 事务中更新；
- 群聊页已支持“暂停”当前本地调度，以及经确认“停止全部 Agent”；停止操作会在一个 SQLite 事务内将 running delivery 标记失败、pending delivery 标记取消，并关闭对应 Run 检查点；
- UI 发送后后台启动 Scheduler，并在 transcript 中展示持久化回复；
- 重新打开项目时自动继续 pending delivery；running/paused/needs-review Run 显示恢复卡片，用户可沿用原 checkpoint 恢复或显式结束；
- 恢复时若 checkpoint 存在未确认的写工具调用，会保持 `needsReview`，不会自动重放副作用；

### Agent Builder 已实现的本地闭环

```text
用户描述所需角色
  → 内置 Builder 使用用户选择的模型
  → project_inspect / model_list / plugin_list_installed
  → agent_draft（terminal，只保存草案）
  → 客户端确认卡片
  → 重新校验当前模型与本机 Plugin allowlist
  → 客户端创建 Agent profile 并加入当前项目 room
```

Builder 自身使用稳定的 `builtin-agent-builder` 项目 Memory subject；新运行在 Memory Engine 暂不可用时仍可生成草案。普通 Agent 不会获得 Builder 工具，也不能在角色 Prompt 或 Plugin 参数中给自己添加创建 Agent、管理成员或额外项目权限。
