## 3. 模块依赖基线

```text
ChatOSApp
  -> ChatOSConnector
  -> ChatOSAPI
  -> ChatOSCore
  -> ChatOSAgentRuntime

ChatOSConnector
  -> ChatOSCore
  -> ChatOSAgentRuntime
  -> SQLite3 / Foundation / platform frameworks

ChatOSAPI
  -> ChatOSCore
  -> ChatOSAgentRuntime

ChatOSCore
  -> Foundation
```

重构后的依赖只能保持或收窄以上方向：

- Core 不得依赖 Connector、API 或 App。
- Connector repository 不得依赖 SwiftUI/App 状态。
- App coordinator 可以组装依赖，但领域 Store 和 Scheduler 不得反向读取 `AppModel`。
- UI 不得直接访问 SQLite handle、对象存储 bucket/object key 或 Run 内真实 ID。
- Windows 移植复用语义与契约，不复用 macOS UI 或平台框架。

## 4. 外部 API 快照

### 4.1 Core 与 Store

- `AgentGroupChat.swift` 在基线包含 74 个 `public enum/struct/protocol` 声明。
- `AgentGroupChatStore` 包含 76 个方法；拆分期间方法名、参数标签、返回类型、`async/throws`、Sendable 边界不得变化。
- `SQLiteAgentGroupChatStore` 继续作为 actor facade，并继续满足：
  - `AgentGroupChatStore`
  - `LocalAgentGroupChatRunStoring`
- 所有 `Codable` 类型必须保持 CodingKeys、raw value、缺省值和旧数据兼容。
- `AgentGroupChatError` case 与本地化错误文本在纯拆分阶段逐字保持。
- `AgentGroupChatValidation` 的 identifier/text/timestamp 规则不得改变。

### 4.3 SQLite

- 当前 schema 版本：24。
- v11 历史 fixture 到 v24 的 golden test 是 Store 拆分门禁。
- SQL 文本、参数顺序、排序、索引、事务边界、默认值、CHECK/FK 约束和错误映射在阶段 1 不变。
- schema bootstrap 与 migration 必须共用同一数据库连接，并保持 WAL、foreign key 和 busy timeout 行为。
- 附件文件提交与消息 SQLite 事务的补偿语义不变；云端 artifact outbox 不进入本地消息主链路。

### 4.4 Scheduler

- 同一账号 drain 串行，不同账号可并行。
- 每个 Agent 同 lane 只 claim 一个 Delivery；manager 与 executor lane 可以按现有规则并发。
- claim、checkpoint、取消、恢复、needs-review、limit-reached 和终态规则不变。
- Task 必须继续由账号/Run 生命周期拥有；不得新增 detached fire-and-forget。

### 4.5 UI

- 群聊、Human–Agent、Agent–Agent 共用消息和附件展示语义。
- 分页、未读、选择、默认滚动到底部、错误恢复、同步重试和 Sheet 行为不变。
- 拆 View 或 ViewModel 时不新增第二份领域事实源；SQLite/服务快照仍是权威状态。
- 用户当前工作区改动存在时，对应文件不得由自动任务机械拆分或覆盖。

## 5. 文件级拆分顺序

1. Core：先移动 error/validation，再移动 Profile/Proposal、Conversation、Todo/Asset、Delivery/Run、Store Contract。
2. Store：先抽 connection/query/transaction 内核与 schema/migrations，再按聚合根移动读写与 row mapper。
3. Tool Provider：先抽 reference vault 与 response DTO，再按 workspace/chat/proposal/todo/asset 分组。
4. Scheduler：先冻结 claim/recovery 测试，再抽 coordinator、planner、executor 和 failure policy。
5. UI：等待用户并行改动合入或明确避让后，依次拆团队工作区、Workspace、ViewModel、AppModel 和 Media/Story。

每个移动提交必须满足：无格式化噪声、无可见 API 改动、最小相关测试通过、完整 `swift test` 通过、独立可回滚。
