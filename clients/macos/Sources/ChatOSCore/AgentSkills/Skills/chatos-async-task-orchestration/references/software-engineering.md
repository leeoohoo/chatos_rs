# Software engineering scenarios

Split feature work when architecture or API decisions gate multiple implementations, when platform paths can proceed independently, or when integration verification needs independent ownership. Keep a small cohesive change in one Task if one worker can implement and verify it safely.

Expected outputs should name changed modules, migrations, tests, artifacts, and compatibility notes. Acceptance criteria should include observable behavior plus proportionate tests, builds, type checks, or manual verification.

When an uncertain failure needs diagnosis to establish the write scope and independent acceptance matters, use `diagnose -> fix -> verify`. Diagnosis reproduces and locates without project writes. Fix consumes the diagnosis, owns the narrow mutation, and runs focused tests. Verification consumes the implemented version, stays read-only, and reruns the relevant user-visible and regression checks itself. A failed verifier reports evidence and triggers a successor fix; it does not repair its own findings. Skip a ceremonial diagnosis when current evidence already identifies the cause, and keep a small known fix with its focused test when no independent handoff is valuable. Review Tasks must inspect actual manifests, source entry points, representative implementations, and tests or CI rather than relying on README text.

For an explicitly new or greenfield project, an empty bound directory, missing `.git`, and absent build manifests are starting conditions, not blockers, when the requested implementation includes creating the project. Put initialization in the implementation Task and proceed. Ask the user only when choosing between an existing repository and a new project would materially change or risk overwriting the target and their intent does not already resolve that choice.

Give parallel coders genuinely disjoint possible write sets, not just disjoint stated objectives. If two coders may modify one file—even different functions—prefer sequential prerequisites or a single write owner with read-only proposals from others. Treat shared contracts, lockfiles, central registries, migrations, generated files, installs and broad formatting as conflict points. Establish uncertain write scope before dispatch, or serialize it; see [graph-patterns-and-dependencies.md](graph-patterns-and-dependencies.md). Use an integration Task when separately valid changes can still fail together. Verification must depend on the implementation version it evaluates and run checks itself rather than repeat the implementer's summary.
