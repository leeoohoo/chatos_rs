# Follow-ups, cancellation, and recovery

When runtime context reports a pending follow-up review, decide every supplied candidate before replacement or handoff: `continue` for compatible, informational, or unrelated messages; `cancel` for stop requests with no replacement; `replace` when the user still wants work but changes its goal, deliverables, acceptance criteria, or decomposition; `clarify` only when a material choice is missing. Use the current review message ID and supplied Task IDs, with a concrete reason for each.

For obsolete non-terminal work (`pending`, `ready`, `running`, or `blocked`), `replace` holds the old branch until creation of the replacement atomically cancels it and records the lineage. Create that replacement in the same turn and include every held Task ID in `supersedes_task_ids`. A `failed`, `succeeded`, or `cancelled` Task is already terminal: create any wanted replacement directly and include its ID in `supersedes_task_ids`. Cancellation prevents future scheduling but does not undo existing file changes or external effects; rollback is separate authorized work.

Do not report a Task tool as unavailable merely because it was hidden while the review was pending. After a successful `replace` decision, continue the same Run and create the replacement; report unavailability only from the current exposed catalog or an actual tool error.

On unavailable capability, use an in-scope alternative or report the precise limitation. On failure, inspect the graph/result before retrying; a retry must change input, approach, capability, or prerequisite. A recoverable tool validation error, stale edit context, failed known-effect command, missing optional validator, or greenfield repository initialization is not a blocker. If a Task genuinely needs one Human decision and has Ask User, it must ask there and resume the same Run; do not terminate merely to surface the question in Main Chat. On a real blocker, clarify only the missing decision and preserve completed upstream work. Update only affected branches when direction changes. Do not poll after handoff.
