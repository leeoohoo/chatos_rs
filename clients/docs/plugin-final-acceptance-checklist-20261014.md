# macOS 插件修复与最终验收清单（2026-10-14）

## 完成定义

本清单只以正式 macOS 客户端中的真实模型调用为最终依据。源码单测、MCP fixture、Run 技术状态 `succeeded` 或“曾生成过候选”都不能单独代表插件可用。

每个插件必须同时满足：工具调用成功、业务验收通过、用户能打开或下载交付物、失败信息可理解、正式安装版本复测通过。不得直接修改插件安装目录、SQLite 状态或信任记录；插件升级必须走正式 Release。复测期间只运行一个 `/Applications/ChatOS.app`，已有任务执行时不重启客户端。

版本核对只属于“正式 Release 发布 + 客户端安装清单”阶段，不属于插件业务黑盒任务。黑盒验收不得要求插件工具、工具 schema 或调用结果自报 Release 版本号，也不得因未返回版本号而降级、判失败或标记证据不足；版本已在任务外核对时，只按真实业务行为和交付物判定。Browser 的打开、真实链接导航、页面读取与会话关闭全部成功，即视为 Browser 业务验收通过。

## 真实用户黑盒入口

最终验收必须从普通用户会自然说出的单项需求开始，需求调研与六类插件任务共七类，分别发起；不得在一条消息里列出全部能力，不得告诉模型插件名、工具名、调用顺序、schema、`structuredContent`、managed Markdown、SHA、Release 版本或内部验收字段。精确结构、文件完整性、依赖关系、耗时和版本均由验收者在任务外核对。包含上述内部实现提示的运行只能作为技术回归证据，不能作为最终真实用户黑盒通过证据。

本轮采用以下自然语言入口（措辞允许等义微调，不增加内部实现提示）：

- 需求调研：“我想给经常加班的上班族做一个‘午后清单’，但还没想清楚先解决哪些问题。帮我把需求梳理清楚，再给我一份可以确认的方案。”
- Document：“帮我把下面这份开业活动说明整理成一份正式的 Word 文档，排版清楚一点，做好后发给我下载。”随后提供标题、日期、三条检查项和两列表格的普通正文。
- Diagram：“帮我画一张咖啡店顾客流程图，流程是到店、排队、点单、取餐、入座，导出成 SVG 发给我。”
- Solution：“我想做一个叫‘午后清单’的小功能，帮我梳理需求并拆成可执行的开发计划。先按两项需求、四个任务整理，最后一个任务要等第二和第三个完成后再开始。需求和实施计划就够了，不用做完整架构设计。”
- Web Design：“帮我设计一个适合咖啡店活动的网页首屏，要有标题、简介和报名按钮，调整到看起来协调后给我预览和交付结果。”
- Browser：“帮我查一下 MiniMax 最近有什么新动态，去官网找到最新的相关新闻，打开后告诉我标题和主要内容。”
- Computer Use：“帮我看一下我现在打开的是哪个 ChatOS 项目。只看，不要点击、输入或修改任何东西。”

需求调研通过标准：系统识别会改变范围或方向的关键未知项并创建一次精简问卷；问卷在项目“需求调研”入口可见；提交纯虚构答案后恢复原对话并生成有来源、版本和待确认状态的具体方案；方案包含目标用户、核心场景、范围与排除项、建议及取舍、阶段产物、验收依据和仍待决定事项；在用户明确授权实施前不得创建执行 Task、修改项目文件或执行外部业务操作。问题已经足够明确时不得强制调研。
