# ChatOS 3.0.8 客户端本地运行面迁移评估与实施方案

状态：**实施中；M1/M2 本地执行内核已落地，M3 本地会话事实源已开始，生产链路尚未切换**

分支：`3.0.8`

基线提交：`a19147c17`（由当前 `3.0.7` 创建）

编制日期：2026-09-29

## 1. 结论

把当前由服务端 Task Runner 创建、调度和执行的任务迁到原生客户端是可行的，而且仓库已经具备大部分基础能力：macOS 和 Windows 都已有本地 SQLite、Agent manager/executor 双 lane、本地模型调用、本地项目工具、本地 Plugin Runtime、取消和崩溃恢复机制。

本次迁移不应把 `task_runner_service/backend` 原样嵌入客户端，也不应继续维护 Swift、C#、Rust 三套 Agent Loop。推荐方案是建立一个随客户端发布的跨平台 Rust `Local Agent Host`，把现有本地 Agent 能力和服务端 Task Runner 中仍有价值的状态机语义收敛到同一个持久化运行内核；SwiftUI 与 WinUI 只通过类型化本地 IPC 使用它。

迁移完成后的边界如下：

- 本机负责：普通对话、会话历史、Task/Run、任务图、Agent Loop、调度、事件、审批、工具、MCP、Plugin 执行、项目和工作区访问、Realtime、本地通知及恢复。
- 服务端保留：Memory Engine、配置与模型控制面、Plugin Marketplace/发布/制品分发，以及支撑这三类能力所需的账号认证。
- 服务端不再负责：主聊天 Agent、Cloud Agent、Task Runner API/Worker/Scheduler、任务回调、MCP 执行路由、Local Connector Relay 或客户端业务数据事实源。

不能把“只把 `create_task` 请求改成本地请求”视为完成。当前任务创建是服务端 Conversation Agent 通过 `task_runner_service` MCP 发起的，任务详情和图又由 `chatos/backend` 代理查询。因此要彻底不走服务端 Task Runner，最终必须同时迁移普通对话 Agent 和会话事实源。

## 2. 用户目标的边界解释

“除了记忆、配置和插件发布平台，其他本地化”在本方案中解释为以下控制面/运行面分离。

### 2.1 保留在服务端的控制面

| 能力 | 保留内容 | 明确不保留 |
| --- | --- | --- |
| Memory Engine | compose、长期记忆、摘要、幂等记录同步 | 本地 Run 状态、任务调度、工具调用推进 |
| 配置与模型 | 账号、模型配置、凭据托管、能力元数据、受管 Prompt/策略 | Agent Loop、会话状态、Task/Run |
| Plugin 平台 | Marketplace、Manifest、Release、签名制品、下载、授权策略 | Plugin 进程、MCP 会话和工具调用执行 |
| Auth | 为上述控制面提供用户、设备和 Token | Task Runner Agent Account、任务级服务端身份 |

模型请求有两个可选部署方式：

1. 推荐：客户端向无状态 Model Gateway 发起一次模型 Step；Gateway 只鉴权、读取模型配置并转发，不保存会话，也不推进 Agent Loop。
2. 可选：客户端获取短期模型凭据后直连供应商。现有 macOS `ChatOSStoryPlanningService` 和 Windows `AgentTeamModelGateway` 已证明该路径可行，但长期凭据不得落入本地业务数据库、日志或 Memory。

这两个方式都不属于服务端 Task Runner。3.0.8 应先定义统一 `ModelStepClient`，避免不同客户端继续各自实现协议。

### 2.2 必须迁到客户端的运行面

- 普通对话的消息落库、Turn 状态、流式事件、追加指令和停止；
- Conversation Agent 的模型/工具循环；
- `create_task`、`create_tasks_with_prerequisites`、启动、取消、重试和任务图；
- Task Runner Agent Profile、运行状态机、事件、进度、结果和人工复核；
- Ask User/审批、工具调用回执及副作用防重；
- 项目文件、Git、终端、远端连接、本地 MCP 和已安装 Plugin 的执行；
- 本地 Scheduler、定时任务、崩溃恢复和 UI Realtime；
- 会话、任务、运行、事件和本地同步 outbox 的权威存储。

## 3. 当前实现评估

### 3.1 当前普通对话和 Task Runner 调用链

当前主链路是：

```text
macOS / Windows UI
  -> POST /api/chatos/agent/chat/send
  -> chatos/backend Conversation Runtime / Cloud Agent
  -> MCP Management runtime session
  -> task_runner_service MCP create_task / create_tasks_with_prerequisites
  -> Task Runner PostgreSQL
  -> Task Runner Scheduler / Worker
  -> MCP Management / Local Connector Service Relay
  -> 原生客户端 Local Connector
  -> 本机项目、终端、Plugin
  -> Task Runner 回调 chatos/backend
  -> WebSocket / compact-history / message-task graph
  -> 原生客户端 UI
```

代码证据：

- macOS `ChatOSConversationCommandService` 和 Windows `ConversationCommandService` 都把新 Turn 发给 `/agent/chat/send`；
- `chatos/backend/src/modules/conversation_runtime/cloud_agent.rs` 在服务端持久化并推进 Conversation Agent；
- `mcp/src/product_skills.rs` 向模型暴露 `create_task` 和 `create_tasks_with_prerequisites`；
- `task_runner_service/backend` 同时承担 API、PostgreSQL Store、Worker、Scheduler、Cloud Agent、MCP、回调和工具运行；
- `chatos/backend/src/api/message_task_runner.rs` 把客户端任务图、Run、重试和取消请求代理到 Task Runner；
- 两端 `MessageTaskGraphService` 仍依赖 `/messages/{id}/task-runner/...`。

因此，当前依赖不是一个 HTTP 创建接口，而是一整条服务端编排闭环。

### 3.2 已具备的本地能力

macOS 已有：

- `ChatOSAgentRuntime`；
- `SQLiteAgentGroupChatStore` 及 Todo、依赖、Delivery、Run、资产和事件表；
- `LocalAgentGroupChatScheduler` 的 manager/executor 双 lane；
- `NativePluginToolBroker`、本地终端、项目文件和 Git 能力；
- Run 取消、Plugin 进程组清理、checkpoint 和崩溃恢复；
- `DurableAgentMemoryService` 的本地缓存与同步 outbox；
- 直接加载受管模型配置并执行模型 Step 的实现。

Windows 已有：

- `SqliteAgentTeamStore`；
- `AgentTeamScheduler`、`AgentTeamBackgroundService`；
- `AgentTeamModelGateway`；
- `AgentPluginToolRuntime` 和本地项目工具；
- manager/executor delivery、Todo DAG、Run 和本地 Plugin 生命周期。

这些能力说明本地化不需要从零开始，但两端目前分别实现了运行循环和存储语义。继续直接扩展两套实现会造成状态机漂移、数据库迁移不一致和安全修复重复。

### 3.3 可复用与不可直接搬迁的部分

| 当前模块 | 处理方式 | 原因 |
| --- | --- | --- |
| 本地 Agent Todo/Delivery/Run 语义 | 抽取并统一 | 已验证本地执行、恢复和取消闭环 |
| 本地 Plugin/项目/终端适配器 | 保留为平台 Adapter | 依赖原生权限和平台 API |
| `chatos_ai_runtime` | 抽取通用模型 Step/上下文能力 | 已有 Rust 运行时基础，但要删除 Cloud 假设 |
| `chatos_cloud_agent_protocol/runtime` | 仅提取 claim、版本、归约、幂等语义 | RabbitMQ/服务路由/Cloud Outbox 不进入客户端 |
| Task Runner Task/Run 状态机和契约 | 选择性移植到公共领域模型 | 现有状态、依赖、审批和完成校验有价值 |
| Task Runner HTTP API、PostgreSQL Store、Worker/Scheduler | 不嵌入客户端 | 面向多租户服务部署，复杂度和信任边界不合适 |
| MCP Management / Local Connector Relay | 从本机任务链删除 | 本地 Host 可直接调用本机 Adapter，无需绕云端 |
| `chatos/backend` 会话 API 和回调 | 用本地 Repository/Event Stream 替代 | 最终会话事实源在本机 |

## 4. 目标架构

```text
┌──────────────────────── ChatOS 原生客户端 ────────────────────────┐
│                                                                  │
│  SwiftUI / WinUI                                                 │
│      │ typed IPC command + event cursor                          │
│      ▼                                                           │
│  Local Agent Host（跨平台 Rust）                                 │
│  ├─ Durable Agent Runtime（一次事件推进一个 Step）               │
│  ├─ MainChatProfile                                              │
│  ├─ TaskRunnerProfile                                            │
│  ├─ Local Scheduler / Recovery                                   │
│  ├─ Conversation / Task / Run Repository                         │
│  ├─ Tool Invocation Ledger / Approval                            │
│  ├─ Memory Sync Outbox                                           │
│  └─ Local Event Stream                                           │
│      │                                                           │
│      ├─ Platform Tool Adapter -> 文件 / Git / Terminal / Remote  │
│      ├─ Plugin Adapter -> 本机 stdio / HTTP MCP / Plugin UI      │
│      └─ Client Storage -> SQLite（3.0.8 默认）                    │
│                                                                  │
└───────────┬────────────────────┬───────────────────────┬─────────┘
            │                    │                       │
            ▼                    ▼                       ▼

       Model Gateway        compose + sync         catalog + artifact
            │                    │                       │
            └────────────────────┴───────────────────────┘
```

### 4.1 客户端自包含模块

实际目录：

```text
clients/local_agent_host
├─ layers/interface
├─ layers/ports
├─ layers/application
├─ layers/profiles
├─ layers/infrastructure/database
└─ src/{application,infrastructure,interface}
```

- `interface`：IPC command/event、领域 DTO、错误码和版本协商；
- `ports`：应用运行时所依赖的持久化接口，不包含数据库连接；
- `application`：Run/Task 状态机、事件归约、claim、重试、取消和工具回执；
- `profiles`：把 `chatos_ai_runtime` 单步结果归约为 durable Run/Tool 转换，并承载 Main Chat/Task Runner 业务 Profile；
- `infrastructure/database`：SQLite Repository/Transaction 和 schema migration，实现 `ports`；
- Host `src`：分为 application 编排、infrastructure 适配和 interface/IPC，不再平铺所有职责。

这些 Local Agent 专用 package 必须全部归属 `clients/local_agent_host`。应用层只依赖 `ports + interface`，不得反向依赖 SQLite 实现。依赖门禁禁止 Host 直接或传递依赖 `chatos/`、`mcp_management_service/`、`task_runner_service/`，保证最终可以物理删除这三个目录。

macOS 与 Windows 不再各自维护完整 Agent Loop。两端保留：

- 原生 UI 和 ViewModel；
- Keychain/Credential Manager；
- 文件选择、系统权限、通知、窗口和 Plugin UI；
- 平台工具执行 Adapter。

### 4.2 Host 生命周期

- Host 与 UI 分进程，UI 崩溃或关闭窗口不应中断正在运行的任务；
- 用户“明确退出 ChatOS”时提示仍在运行的任务，可选择继续后台、暂停或取消；
- macOS 使用用户级 LaunchAgent/受管 helper，Windows 使用用户会话后台进程或托盘宿主；
- 断电、系统重启和 Host 被 kill 后依赖 durable event/lease 恢复；
- 不承诺用户登出或机器关机期间继续执行，但恢复后不得重复副作用。

## 5. 公共运行时设计

### 5.1 一个 Runtime，两个业务 Profile

`MainChatProfile` 负责：

- 组装当前 Turn 的上下文和可用能力；
- 判定直接回复、Ask User 或创建后台任务；
- 把 `create_task` 工具调用写入本地 Task Repository；
- 将任务引用写回当前 Turn，但不轮询任务完成。

`TaskRunnerProfile` 负责：

- 加载冻结的执行契约、项目授权、Plugin/Skill 快照和依赖结果；
- 生成进度、调用本机工具、阻塞、请求审批或完成；
- 校验完成证据和工作区变更；
- 将终态事件投递回来源 Conversation。

二者只能提供业务决策，不能各自实现循环、重试或另一份消息历史。

### 5.2 单步持久化状态机

每次推进固定为：

```text
claim event + load run/version
  -> prepare exactly one model/tool/reducer step
  -> execute bounded operation
  -> transactionally persist outcome + next events + outbox
  -> release claim
```

Run 状态至少包括：

```text
queued
model_ready
model_running
waiting_tool_result
continuation_ready
waiting_user
retry_scheduled
paused
needs_review
succeeded
failed
cancelled
```

强制规则：

1. 工具调用必须先落库再执行；
2. 工具结果必须使用原始 `call_id` 幂等落库；
3. 读操作可按策略安全重试；
4. 写文件、Git、终端、Plugin 等副作用结果未知时进入 `needs_review`，不得自动重放；
5. Run 终态必须由 Profile 的完成校验确认，迭代上限不能等价于成功；
6. 同一 Task 同时最多一个活动 Run；同一执行 lane 的 claim 使用 version/CAS 和租约保护；
7. 所有定时器只产生 durable event，不把长时间 sleep 作为任务状态。

## 6. 本地数据模型

3.0.8 首先交付 SQLite；Repository 接口不得暴露 SQLite 类型，以便后续按既定最终架构增加用户自有 PostgreSQL。

### 6.1 核心逻辑表

| 聚合 | 表 |
| --- | --- |
| Conversation | `conversations`、`turns`、`messages`、`message_attachments` |
| Task | `tasks`、`task_dependencies`、`task_sources`、`task_snapshots` |
| Run | `agent_runs`、`run_events`、`run_checkpoints`、`run_leases` |
| Tool | `tool_invocations`、`tool_results`、`approval_requests` |
| Delivery | `local_events`、`event_consumers`、`scheduled_events` |
| Sync | `memory_sync_outbox`、`memory_sync_cursors` |
| Local platform | `installed_plugin_snapshots`、`workspace_authorizations` |

### 6.2 Task 模型

不要直接把团队 `local_agent_todos` 改名成普通 Task。应先抽取公共 `TaskRepository`，再让团队 Todo 和普通 Message Task 使用统一内核、不同 Profile/来源字段。

Task 至少保存：

- `task_id`、`owner_user_id`、`profile_key`；
- `source_conversation_id`、`source_turn_id`、`source_message_id`；
- 标题、目标、范围、输出、验收条件、约束；
- 优先级、状态、父任务和 DAG 依赖；
- 冻结的项目/工作区授权；
- 冻结的模型配置 revision（不含密钥）；
- Plugin Release、Component、Skill、权限和配置快照；
- 当前 Run、结果、阻塞原因和创建/更新时间。

### 6.3 状态兼容

服务端历史状态与新本地状态通过 DTO Mapper 兼容现有 UI，不让 UI 直接依赖数据库枚举：

| 服务端 Task Runner | 本地领域含义 |
| --- | --- |
| `draft` | `draft` |
| `ready` / `queued` | `pending`，是否可运行由依赖和 schedule 派生 |
| `running` | `in_progress` |
| `succeeded` | `succeeded` |
| `failed` | `failed` |
| `blocked` | `blocked` |
| `cancelled` | `cancelled` |
| `archived` | 独立 `archived_at`，不作为执行状态 |

Run 的模型阶段、集成阶段、事件分页和变更摘要继续作为独立字段/事件提供，保证现有 Task Inspector 可以平滑切到本地 Service。

Graph 聚合状态不单独持久化，而是从本地 Task 权威行实时派生：尚未开始为 `pending`，已有执行进展且仍有活动 Task 为 `running`，全部成功为 `succeeded`，包含失败的终态图为 `failed`，无失败但因取消终止为 `cancelled`。Task Inspector 通过 `get_task_runs` 按新到旧读取指定 Task 的历次 Run（单次最多 100 条），因此重试不会覆盖失败或取消的历史执行记录。

## 7. 本地 IPC 与客户端接入

### 7.1 IPC 原则

- macOS 使用受应用容器保护的 Unix Domain Socket/XPC 包装；
- Windows 使用按用户 ACL 限制的 Named Pipe；
- 每次连接校验当前用户、安装身份和协议版本；
- command 使用幂等 `command_id`；event 使用单调 cursor，可断线重放；
- IPC 不传长期模型密钥、Plugin Secret 或不受限文件路径；
- 大附件只传受授权文件引用和内容 hash，不传无界 Base64。

### 7.2 保持 UI 接口稳定

第一轮不重写 UI。新增本地实现替换当前 API 实现：

macOS：

- `ConversationCommandServicing` -> `LocalConversationCommandService`；
- `ConversationRemoteServicing` -> `LocalConversationHistoryService`；
- `ConversationRealtimeStreaming` -> `LocalConversationEventStream`；
- `MessageTaskGraphServicing` -> `LocalMessageTaskGraphService`。

Windows：

- `IConversationCommandService` -> 本地实现；
- `IConversationHistoryService` -> 本地实现；
- `IRealtimeClient` -> 本地 event cursor 实现；
- `IMessageTaskGraphService` -> 本地实现。

现有 ViewModel、Task Graph 和 Inspector 先只切依赖注入，待功能等价后再删除服务端 DTO。

## 8. Memory、配置和 Plugin 的联网方式

### 8.1 Memory

- 每个 Conversation/Task 使用稳定、本地生成的 thread/record ID；
- 本地记录和运行不以 Memory 在线为前提；
- 先写本地 immutable record 和 `memory_sync_outbox`，再异步上传；
- Memory 故障时使用最近一次 compose 缓存并继续运行；
- 恢复后以相同 record ID 幂等补传；
- Memory 内容不能扩大工具或工作区权限。

macOS 现有 `DurableAgentMemoryService` 可作为行为基线，最终同步逻辑进入公共 Rust 内核，避免 Windows 另写一套。

### 8.2 配置与模型

- 本地缓存不含密钥的配置 revision 和运行快照；
- 开始一个 Run 时冻结 model/provider/capability revision；
- 密钥只在一次 Model Step 的短生命周期内存在于受保护内存；
- 配置更新只影响新 Run，运行中的 Run 不静默换模型；
- Config Center 管服务端基础配置，客户端 Runtime 限额通过签名配置快照下发并缓存。

### 8.3 Plugin

- Plugin 平台继续提供目录、Release、签名制品和策略；
- 客户端下载后验证 hash/签名，写入不可变安装快照；
- Task 创建时只选择语义能力，Host 解析为可信 Release/Component/Skill 快照；
- 运行时直接调用本机 Plugin Adapter，不经过 MCP Management 或 Local Connector Service；
- Plugin Secret 留在 Keychain/Credential Manager；
- 每个调用仍执行权限、审批、超时、取消、进程组清理和 artifact 注册。

## 9. 迁移阶段

### 阶段 0：契约冻结和可测基线

1. 为 Conversation、Task Graph、Run Detail、Realtime、Ask User、Task MCP 工具建立 golden contract；
2. 固定当前 Task/Run 状态、错误码、取消和重试语义；
3. 为 macOS/Windows 本地 Scheduler 建立相同场景的行为测试；
4. 记录服务端链路的关键时延、失败率和 API 使用清单；
5. 增加 `local_runtime_v2` 开发开关，但生产默认仍走旧链路。

退出条件：旧实现的行为可由自动化判定，新内核有明确兼容目标。

### 阶段 1：公共 Protocol、Storage 和 Host 骨架

1. 创建四个公共 Rust 模块；
2. 实现 SQLite schema、migration、事务、备份和 integrity check；
3. 实现 IPC 握手、command 幂等和 event cursor；
4. 实现 Run/Event/Tool ledger，不接真实副作用工具；
5. 两端客户端完成 Host 启停、健康检查和依赖注入。

退出条件：两端能创建本地测试 Run，kill Host 后恢复并继续消费无副作用事件。

### 阶段 2：Task Runner Profile 本地化

1. 实现本地 `create_task`、批量带依赖创建、更新、取消、启动和查询工具；
2. 移植 Task execution contract、DAG 校验、单活动 Run、进度和完成校验；
3. 接入本地项目、文件、Git、终端、远端连接和 Ask User Adapter；
4. 接入本地 Plugin/Skill 快照和执行；
5. 实现 `LocalMessageTaskGraphService` 和 Run Inspector 数据源；
6. 只对开发账号/新建测试任务启用，不接服务端任务双写。

退出条件：显式从客户端创建的任务完全不访问 Task Runner、MCP Management 和 Local Connector Service，且两端行为一致。

### 阶段 3：Main Chat Profile 和本地会话事实源

1. 将普通 Conversation Agent 放入公共 Runtime；
2. 本地保存 Conversation/Turn/Message，并通过本地 event stream 驱动 UI；
3. 把 `create_task` 工具绑定到本地 Task Repository；
4. 实现 guidance、stop、Ask User、附件和任务终态回写；
5. 用本地 History/Realtime/Command Service 替换 `/agent/chat/*`、WebSocket 和 compact-history；
6. Memory Engine 只接收异步记录，不再拥有客户端执行状态。

退出条件：新 Conversation 从发送消息、创建任务、执行、回写到查看任务图全程不经过 `chatos/backend` 运行面。

### 阶段 4：切换与旧服务端数据处置

切换规则：

- 切换前禁止创建新的云端任务；
- 云端 `queued/running` Task 不迁移，切换前必须完成或取消；切换后如仍需执行，由用户显式新建本地 Task；
- 不把云端历史 Conversation/Task/Run 导入本地数据库，不保留 legacy 映射，也不在本地 UI 合并新旧任务图；
- 旧服务端数据仅按既有保留/删除策略留在原系统，不能成为本地 Host 启动或执行的依赖；
- 不执行 SQLite/服务端双写，不允许同一个 Task 同时由云端和本地 Scheduler claim；
- 切换标记以账户 + 设备持久化，回滚只能停止本地新执行后进行，不能把本地 Run 倒灌为云端可执行任务。

退出条件：新任务只在本地产生，本地产品链路不读取或导入旧云端 Task/Run 数据。

### 阶段 5：下线服务端运行面

按依赖逆序删除：

1. Task Runner callback 和 `chatos/backend` message-task proxy；
2. MCP Management 中 Task Runner/ChatOS 的运行路由；
3. Local Connector Service 的任务执行 Relay（如无其他远控需求则整体下线）；
4. `task_runner_service` Scheduler、Worker、API 和数据库写入；
5. `chatos/backend` Conversation Cloud Agent、会话执行和 Realtime；
6. Task Runner Agent Account、token exchange、mTLS secret、APISIX route、Compose service 和管理台页面；
7. RabbitMQ 中对应 routing key、outbox reconciler 和监控告警。

服务端仓库代码先标记只读/冻结一个发布周期，再删除，便于对照迁移但不允许生产继续写。

退出条件：生产部署只保留控制面服务；Task Runner、ChatOS Runtime、MCP Runtime 和 Local Connector Relay 不再是客户端可用性的前置条件。

### 阶段 6：默认开启和清理

1. 删除 `local_runtime_v2` 旧链路开关；
2. 删除客户端服务端 Conversation/Task DTO 和代理 Service；
3. 更新 README、部署拓扑、安装说明和管理台；
4. 更新数据导出、诊断包、隐私说明和故障排查；
5. 完成 macOS/Windows 同版本发布和升级演练。

## 10. 不采用的方案

### 10.1 把 Task Runner Rust 服务作为 localhost HTTP 服务直接打包

不采用。它会把 PostgreSQL、服务认证、多租户 API、Cloud Agent、服务发现和运维逻辑一并带入客户端，仍然保留错误的服务边界。

### 10.2 只把工具执行本地化

当前已经基本如此，但 Task、Run 和 Agent Loop 仍在服务端，不能满足目标。

### 10.3 Swift 和 C# 分别复制 Task Runner

不采用。两端现有本地团队能力适合作为行为参考和平台 Adapter，不适合作为两套长期内核。

### 10.4 云端和本地长期双写/双执行

不采用。Task claim、工具副作用、Run 终态和回调无法通过最终一致性安全合并。灰度只能按账户/设备/Conversation 明确单路由。

## 11. 风险与控制措施

| 风险 | 控制措施 |
| --- | --- |
| 客户端退出导致任务中断 | 独立 Host、durable event、启动恢复、显式退出策略 |
| 副作用重复执行 | 调用前 ledger、稳定 call ID、结果未知进入 `needs_review` |
| SQLite 损坏或升级失败 | WAL、事务 migration、启动 integrity check、迁移前备份、staging 替换 |
| 两端行为漂移 | 公共 Rust 内核、协议契约测试、相同 fixture 和状态机测试 |
| 模型密钥暴露 | 无状态 Gateway 或短期凭据、系统安全存储、日志脱敏、不进入业务库 |
| Plugin 供应链风险 | 签名/hash、不可变 Release 快照、权限审批、进程隔离和清理 |
| Memory 离线 | 本地缓存/outbox、幂等补传、执行不依赖 compose 在线 |
| 多设备同账号冲突 | 任务数据默认设备本地权威；不宣称跨设备同步，不自动合并不同设备任务 |
| 历史云端活动任务丢失 | 切换前 drain/cancel；旧任务不迁移，禁止热迁移和双 claim |
| 本地数据库无限增长 | 事件分层保留、诊断 payload 上限、可验证归档和 vacuum 策略 |

## 12. 验证与验收

### 12.1 自动化门禁

- Rust：Runtime reducer、CAS/lease、SQLite migration、IPC、crash recovery、tool ledger；
- macOS：本地 Service mapping、Host lifecycle、Plugin/终端取消、UI Task Graph；
- Windows：相同协议、Named Pipe ACL、Host lifecycle、Plugin/终端取消、UI Task Graph；
- contract：同一 fixture 在 macOS/Windows 映射出相同 Task/Run/Realtime 结果；
- migration：仅覆盖本地旧 schema 的增量升级和失败回滚，不覆盖云端历史业务数据导入；
- security：路径逃逸、跨用户 IPC、伪造事件、重放 command、Secret 泄漏扫描。

### 12.2 故障注入

- 在模型返回前、工具落库后执行前、工具执行后结果落库前分别 kill Host；
- Memory、配置和 Plugin 平台分别断网；
- Plugin 子进程失联或生成后代进程；
- SQLite busy、磁盘满、migration 中断；
- UI 与 Host 断连重连，event cursor 重放；
- 系统睡眠/唤醒、网络切换、账号退出。

### 12.3 最终验收标准

1. 屏蔽 `chatos-backend`、`task-runner`、`mcp-management`、`local-connector-service` 后，已登录客户端仍能完成普通聊天、本地任务、取消、审批、重试、任务图和 Plugin 执行；
2. 客户端联网时只访问 Auth、配置/模型、Memory 和 Plugin 平台允许的 API；
3. 任务执行期间无请求命中 Task Runner API、Worker、callback 或服务端 MCP 路由；
4. Host 被 kill 后能恢复，任何副作用工具都不会无条件重复；
5. Memory 离线时任务继续，恢复后记录按稳定 ID 补传；
6. macOS 与 Windows 对同一执行 fixture 产生等价状态、事件和错误码；
7. 旧云端 Task/Run 不导入本地，新任务只存在本地；
8. 部署清单中 Task Runner API/Worker/Scheduler、Conversation Cloud Agent、MCP Runtime Relay 均已删除；
9. 本地数据库、日志和诊断包不包含长期模型密钥或 Plugin Secret；
10. README 和产品 UI 不再把云端 Task Runner 描述为运行前置条件。

| --- | --- | --- |

| M1 | 公共 Runtime/Storage/IPC/Host | 高 |

### 13.1 M1 当前实施状态

已在 `3.0.8` 分支落地第一批 Rust Local Agent Host 基础：

- `chatos_local_agent_protocol`：版本化的长度前缀 JSON 协议、请求校验、Run/Event DTO 和稳定错误结构；
- `chatos_client_storage`：SQLite migration、Run/Event 持久化、单写事务、命令回执、事件 cursor 和按调用持久化的 Tool Invocation Ledger；
- `chatos_local_agent_runtime`：Run 创建、claim lease、CAS 提交、取消、重试/暂停/人工复核/终态转换，以及公共 `LocalAgentProfile` 注册边界；
- `clients/local_agent_host`：Unix Socket、Windows Named Pipe 和 stdio 传输，含 1 MiB frame 上限、受保护的本机 IPC 权限和单步 Profile Scheduler；
- 崩溃恢复采用保守策略：过期的 `model_running` claim 进入 `needs_review`，不自动重放结果未知的副作用。
- Tool claim 过期时，只读调用可回到 `pending`，副作用调用进入 `needs_review`；批次全部落库后 Run 才能继续。
- Run 持久化 Profile 不透明 checkpoint 和一次性 continuation payload，工具结果、用户回复和人工恢复在 Host 重启后仍可作为下一次模型 Step 的明确输入。
- `chatos_agent_profiles` 已接入 `chatos_ai_runtime` 的单步执行结果；正式回答、continuation、模型重试和工具调用统一转换为 durable outcome，未显式标记只读的工具默认按副作用处理。
- Host 已提供 `LocalToolRegistry` 和单调用 Tool Scheduler；平台适配器只实现一次工具执行，claim、回执、批次完成和未知副作用的安全转移由公共 Host 负责。
- Host 已提供事件驱动 `LocalAgentHostCoordinator`，把模型与工具 Scheduler 组合为持续执行循环：stdio、Unix Socket 和 Windows Named Pipe 均可把请求直接交给 Coordinator，成功 IPC 命令即时唤醒，一次唤醒持续推进到无可运行工作；`retry_scheduled` 只按 SQLite 中最早的 durable deadline 设置定时器，空闲时不轮询。
- 模型瞬时重试的 `model_attempt` 已进入 Run 持久化状态和 SQLite v4 migration；Retry transition 会保留尚未被模型成功消费的工具/用户 continuation，Host 重启或重新 claim 后既不会丢输入，也不会退回 attempt 1 绕过重试上限。
- `chatos_agent_profiles` 已提供 Main Chat/Task Runner 共用的 `ControlPlaneLocalAiStepPlanner`：每个 Step 按 `model_config_ref + revision` 和 capability revision 瞬时解析模型、Prompt 与工具，把 checkpoint、工具结果或用户恢复输入重建为 Responses history；包含 API key 的 `ModelRuntimeConfig` 不进入 durable Run 或 checkpoint。
- `clients/local_agent_host` 已提供 `LocalAgentHostAssembly` 作为原生客户端装配根：传入同一个 Runtime、控制面 Resolver 和平台 Tool Registry 后，统一注册 `main_chat`/`task_runner` Profile，并构造 Model Scheduler、Tool Scheduler 与 Coordinator，避免 Swift/C# 各自拼装运行循环。
- Host 已提供 `LocalControlPlaneSnapshot`：原生客户端认证后按精确 revision 发布模型配置与 capability 快照。SQLite v11 通过独立 `LocalCapabilitySnapshotStore` 端口持久化有界、不可变且不含密钥的 instructions、前置输入和工具定义；SQLite v12 通过 `LocalModelConfigSnapshotStore` 持久化不含 API key 的 model/provider 请求配置和原生凭据引用。Host 重启后可按 Run 冻结的两个 revision 恢复，执行前才由 `LocalModelCredentialResolver` 从 Keychain/Credential Manager 解析密钥并组装瞬时 runner。Run 与控制面数据库均不保存密钥，也不固化请求级 cache key、response ID 或工作目录。
- `LocalAgentHostAssembly::with_external_tool_worker` 支持 Swift/C# 通过 IPC 直接 claim/commit durable Tool Ledger；平台权限、文件选择器和 Plugin UI 可继续留在原生进程，Rust Coordinator 在工具回执后推进模型，不需要原生端再实现 Agent Loop。
- IPC v3 新增有界 `wait_events`（最长 60 秒）：外部 Tool Worker 按 durable cursor 等待 `tool_batch_requested` 等事件后再 claim，不产生空轮询和空 claim receipt；超时返回空事件页且不推进 cursor。
- IPC v4 新增 `create_task_graph` / `get_task_graph`，SQLite v5 新增本地 Task Graph、Task 和 Dependency 权威表；整张 DAG 先完成同图引用、重复边、自依赖和环校验，再以单事务和 command receipt 幂等写入。无前置依赖的 Task 初始为 `ready`，其余为 `pending`，查询结果按 Task ID 和依赖边稳定排序。
- Model Scheduler 会把每个 `ready` Task 原子物化为唯一活动 Run；Run 成功时同事务归约 Task 并解锁全部前置条件已成功的后继，Run 失败或取消时递归把依赖链标记为 `blocked`。Run 创建和 Task 终态归约都会产生 durable event，Host 重启不会重复启动已进入 `running` 的 Task。
- IPC v5 新增幂等 `cancel_task` / `retry_task`：取消运行中 Task 会在同一事务终止活动 Run 并阻断后继；重试只接受版本匹配、前置依赖已满足的失败/取消 Task，并重算由它导致的下游 `blocked` 状态后生成新 Run。
- Host Assembly 已把 `create_task` / `create_tasks_with_prerequisites` 注册为 Rust 本地工具：使用 durable invocation ID 派生稳定 Graph/Task ID，直接写入本地 Task Repository，并继承父 Run 的精确模型与 capability revision。当前只接受同一次批量调用内的 `prerequisite_refs`；跨 Graph 前置依赖和未解析的模型切换会明确拒绝。
- IPC v6 为 Tool claim 增加 `include_tool_names` / `exclude_tool_names`。外部 Tool Worker 模式下，Rust worker 只 claim 两个保留的 Task 工具，Coordinator 会在所有原生 IPC claim 上自动排除它们，Swift/C# 继续执行文件、Git、终端和 Plugin 等平台工具，不会与 Rust 竞争同一 invocation。
- IPC v7 为 `get_task_graph` 增加查询时派生的 Graph 聚合状态，并新增 `get_task_runs`：按 Task 返回最新优先、最多 100 条的本地 Run 历史，重试产生的新旧 Run 均可由 Task Inspector 追溯；不存在的 Task 明确返回 `not_found`。
- IPC v8 新增带精确版本和原因的幂等 `restart_task`。它只接受运行中或终态 Task，在一个事务内取消目标和传递下游仍在运行的 Run，把目标重置为 `ready`、全部传递下游重置为 `pending`，并保留旧 Run 历史；前置依赖不满足、版本过期、尚未开始或被阻塞的 Task 均拒绝强制重启。
- IPC v9 与 SQLite v6 新增本地 Plugin/MCP 安装快照；本地 MCP stdio 会话直接完成初始化、工具发现和调用，Secret 仅以系统凭据引用持久化，执行不经过 `mcp_management_service`。
- IPC v10 与 SQLite v7 新增本地 Conversation、Turn、Message 权威存储。开始 Turn 时以单事务创建用户 Message、`main_chat` Run、事件和幂等回执；Run 成功、失败或取消时在同一终态事务中关闭 Turn，且仅成功时追加助手 Message。不导入旧服务端 Conversation 数据。
- IPC v11 与 SQLite v8 新增本地 Message 附件引用。数据库只保存有界元数据、顺序、大小、SHA-256 和原生客户端签发的 opaque 授权引用，不保存文件体或 Base64；Main Chat Planner 只向模型提供资源清单，内容读取仍由 capability-approved 本地工具完成。
- SQLite v9 新增本地 Task Graph 终态回写账本。来源为 `conversation_turn` 的 Graph 在成功、失败或取消后，把 Graph 状态和各 Task 最新终态结果作为结构化助手 Message 与最终 Task 状态原子提交；终态签名防止重放产生重复消息，重试或强制重启后的新终态则形成下一代回写，全程不调用 Task Runner callback 或 `chatos/backend` message proxy。
- IPC v12 新增 Conversation 专用 `resume_conversation_turn` / `cancel_conversation_turn`。Ask User 回复会在一个 SQLite 事务中校验 Conversation/Run 精确版本、追加用户 Message 和附件引用、写入 continuation 并恢复 Run；停止操作会校验 Turn 所属 Run、取消 Run、失效未完成工具调用、关闭 Turn 并推进 Conversation 版本。两者均使用 durable command receipt 防止重放重复写入，不借道服务端 Conversation 或 Task Runner。
- IPC v13 新增 `get_conversation_history` 本地历史分页。它以 Message ordinal 作为排他性 `before_ordinal` 游标，每页最多返回 100 条按时间正序排列的 Message，并只携带本页关联的 Turn 和附件；`next_before_ordinal` 明确表示是否还有更早页面，从协议层避免长会话通过无界响应触碰 1 MiB IPC frame 上限。
- IPC v14 与 SQLite v10 新增 `guide_conversation_turn` 和本地 guidance 队列。追加指令的用户 Message、附件引用、队列行、Run/Conversation 版本和事件原子提交；若模型 Step 正在执行，旧 claim 会被显式失效，其迟到结果不能覆盖新指令，Scheduler 将这类受控抢占归约为继续执行；若 Run 正在等待工具，guidance 会在下次 claim 时与 durable tool results 合并，且每条指令只交付一次。
- SQLite v11 新增本地 capability policy revision 快照。配置控制面发布的非敏感 instructions、前置输入和工具 schema 通过存储端口按 `profile_key + revision` 不可变落库，重复发布相同内容幂等、复用 revision 篡改内容会冲突；Host 重启后 Resolver 可按已有 Run 的冻结 revision 重新装载。模型 API key 和执行 runner 仍只在原生凭据解析后的进程内存中存在。
- SQLite v12 新增本地 model config revision 快照。`LocalModelConfigSnapshot` 在类型和数据库列上均不包含 API key，只保存 model/provider、能力标记、有界请求参数、结构化输出格式及系统凭据引用；相同 revision 重复发布幂等，复用 revision 修改内容会冲突。恢复执行时才解析凭据引用并与进程内 `ContextualTurnRunner` 合成瞬时配置，密钥不进入持久层。

当前交付包含 M1 持久化运行内核、模型/工具单步执行框架、控制面解析 Planner 边界、事件驱动 Coordinator、IPC 宿主，M2 的 Task DAG 权威存储、Task→Run 调度、依赖解锁、Task/Graph 状态归约、取消、受版本保护的重试与强制重启、Task Run 历史查询、Main Chat 本地建任务工具和外部 Tool Worker 安全分流，以及 M3 的 Conversation/Turn/Message/Attachment 本地事实源、Main Chat Run 原子创建、guidance/Ask User/停止原子控制、本地历史分页和 Task Graph 终态本地回写。尚未实现实际控制面数据源、平台工具适配器、完整 Main Chat/Task Runner 业务策略、原生客户端生命周期接入或生产流量切换。在这些能力落地前，现有服务端 Task Runner 仍是生产任务链路的一部分。

建议 3.0.8 的第一个可交付切片是：

1. 冻结 Message Task Graph/Run contract；
2. 建立公共 Rust Host + SQLite + IPC；
3. 支持客户端显式创建一个无依赖本地 Task；
4. 使用本机模型和只读项目工具执行；
5. 在现有 Task Inspector 中查看本地 Run；
6. kill/restart Host 后恢复；
7. 全程确认没有 Task Runner 网络请求。

这个切片验证最关键的技术路径，同时不提前迁移普通聊天或破坏现有生产任务。
