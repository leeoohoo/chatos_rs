# Graph patterns and dependencies

- `prerequisite_refs` is blocking. Use it only when a downstream Task needs an upstream artifact, decision, schema, or verified fact.
- `context_refs` is non-blocking metadata. It neither delays scheduling nor guarantees another Task's result is available.
- `prerequisite_task_ids` links to already persisted Tasks in the allowed scope.

Useful patterns are parallel specialists then synthesis; investigation then action; shared contract then parallel implementations; and implementation followed by independent review. Do not encode chronology as dependency: if two Tasks can start from the original request, leave them independent.

## Check possible shared-file writes before parallelizing

Independence of goals is not independence of mutations. Compare the files each Task may change, not just its title, role or declared primary output. When two Tasks may modify the same file, prefer a real sequential prerequisite. Two edits to different functions, paragraphs, cells or layers of the same file still share one write target. Do not invent disjoint `owned_paths` while actual commands/plugins can touch both ranges.

Include indirect writes: formatters, code generators, dependency installs/lockfiles, migrations, generated indexes, shared registries, design source files, document/deck workbooks and exported artifacts. If overlapping edits are tightly coupled, one Task should own the write; other Tasks may return read-only findings or proposals for that owner to integrate. If the second writer needs the first change, make that prerequisite explicit rather than relying on a runtime lock to choose the correct order.

When write scope is unknown, first inspect/establish ownership or serialize potentially conflicting writers. Read/read tasks may remain independent. A reader/reviewer that must assess a writer's finished version must depend on it; don't review a moving version as if it were the accepted result. Keep clearly disjoint work independent—do not serialize an entire project just because unrelated paths exist. Runtime overlap rejection/locks are a final safety net, not a substitute for this planning decision.

Give concurrent writers narrow, disjoint `owned_paths`, including known files or directories written indirectly by Plugins. Graph creation rejects unordered `CodeMaintainerWrite` Tasks when one path equals or contains another; an empty CodeMaintainerWrite list claims the whole project. The scheduler holds path locks while a Task has an active Run, so overlapping writers from other graphs in the same project or non-project conversation wait while unrelated readers and disjoint writers can proceed. Lock comparison conservatively includes case and Unicode normalization aliases. The native editor freezes the declared range into each Task edit session and rejects writes outside its exact paths or descendants, including ancestor deletion and symbolic-link parents. `TerminalController` and External MCP execution take the entire-project runtime lock. Plugin-only Tasks instead take a per-Plugin runtime lock plus their declared paths: different Plugins with disjoint outputs may execute in parallel, while Tasks using the same Plugin or the same declared file remain serialized. If a Plugin's mutation scope is uncertain, inspect first or add a prerequisite rather than pretending it is independent. Completion, cancellation, and expired-claim reconciliation release locks. Paths must be normalized and project-relative, using `/` without empty, `.` or `..` components. If two Tasks must edit the same source of truth or use potentially unbounded capabilities in a required order, serialize them with a prerequisite or give one ownership while the other returns a proposal or review.

## Progress and final delivery

`progress_summary` is the default for new multi-Task work. At the worker's first actual claim, each Task writes a short named status message to Main Chat; creation, queueing and waiting for prerequisites are not starts. Completion, failure, blocking or user cancellation updates that same per-Run message. Failures/blockers include a short sanitized reason; successful reports stay out of progress messages. Model retries within a Run do not create extra start messages. A user-requested Task retry has a new Run and its own progress message.

For parallel specialists followed by synthesis (development review, design proposals, copy variants, research, finance audit or mixed artifacts), set graph-level `final_delivery_ref` to the final Task's `client_ref`. This Task must depend directly or transitively on every other Task in the graph. Its contract must require a complete user-facing deliverable that consumes upstream evidence, distinguishes verified facts from unverified claims, and includes requested artifact paths/links or next decisions. The runtime delivers its full sanitized result once after the graph finishes, not a 420-character preview. A marker identifies the delivery owner; it does not prove that the content meets acceptance criteria.

Do not add a synthesis Task just to repeat independent outputs. Without `final_delivery_ref`, the runtime delivers available full reports together in one final message. If synthesis is failed/blocked/cancelled, final delivery states the graph's actual outcome and includes available successful reports; never claim a complete synthesis. Detailed reports remain accessible in the Task workspace.

Quiet `graph_summary` retains the legacy no-start behavior and is opt-in only when the user requests no intermediate progress. `milestones` publishes marked Tasks, failures/blockers and a final summary; `all_tasks` retains legacy per-Task callbacks. Persisted policies are not rewritten. A terminal signature unchanged by a repeated callback does not produce another final message; a Task retry that changes the terminal signature creates a new generation.

Use stable `client_ref` values such as `api-contract`, `mac-implementation`, and `integration-qa`. Put original shared inputs in every Task that needs them. When a downstream Task needs an upstream result, use a prerequisite and state what it consumes. Remove unnecessary transitive edges.
