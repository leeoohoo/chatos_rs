## 用户要求基线

- 每个真实 Agent 都有独立且稳定的 Agent ID；`main_chat`、`task_execution` 等运行 profile 不是 Agent。
- 叽咕狸的 Main Chat、项目会话和普通会话都属于 `agent:jiguli`；其他 Agent 与叽咕狸平级，不能归到叽咕狸。
- 同一个 Agent 的普通会话使用稳定 Agent Thread；Task/Todo 每个任务使用独立 Thread。
- Task/Todo 结束后，其有效总结必须汇入执行 Agent Memory；有项目时同时汇入对应 Project Summary。
- 每次模型请求都必须携带当前 Agent Memory、当前项目总结、当前 Thread 最近总结和尚未被总结的近期记录。
- 本地审批 Agent 使用自己的稳定 Agent Thread，不能每次审批创建新 Thread，也不能每次审批结束就主动总结；累计达到配置阈值后再由 Memory Engine 总结。
- `room_id` 只用于来源追踪，不参与 Memory 身份或召回范围。
- 不做历史数据兼容迁移；不添加 Memory 故障时无记忆继续运行的降级逻辑。
- Memory 策略统一来自配置中心，不保留无依据硬编码。
- 每项修复后必须测试；本轮完成后提交并推送当前分支。

### ME-03 普通 Task 独立 Thread 与归并

### ME-06 自动 Summary、Rollup、Agent Memory、Project Summary 作业

- 状态：已完成
- 验收：待处理记录达到配置阈值后能自动生成 Thread Summary；Summary 能继续生成 Rollup，并分别进入 Agent Memory 与 Project Summary；作业不会因缺失旧硬编码参数而停摆。
- Summary 触发证据：worker 每次读取 Configuration Center snapshot 覆盖后的 `summary.token_limit`；缺失配置会明确报错，不再使用 6000/700 或运行时默认值。真实 PostgreSQL 测试验证低于配置阈值不入队、达到阈值才创建普通 dispatch，Task/Todo terminal forced dispatch 则独立于普通阈值。
- forced 边界修复：初始 `dispatch_version=0` 与 `force_version=0` 原会因 `0 >= 0` 被误判为 forced，导致未达阈值的新 Thread 进入候选扫描。现统一要求 force version 大于 0，并新增单元及真实数据库回归测试。
- Thread Summary 事务证据：Summary 正文、rollup dispatch 和 subject-memory source dispatch 在同一条 `engine_summaries` INSERT 中持久化；不存在“摘要已落库但后续归并事件丢失”的窗口。
- Rollup 证据：数据库 worker claim 持久化 dispatch；失败记录错误并 defer；stale claim 可恢复；处理后若仍有可聚合 Summary 会继续 rearm。Rollup settings 的 `token_limit/count_limit/keep_level0_count/max_level` 全部来自配置中心 policy，缺失时拒绝运行。
- Agent/Project 归并证据：每个 `memory-schema:v2` Thread 自动注册 `agent_memory` identity scope；项目绑定 Thread 同时注册 `project_summary` scope。稳定 Agent Thread 跨项目时，Summary 持久化 `project_subject_id`，Project selector 同时匹配 Thread label 或该 Summary metadata，因此不会把不同项目混在一起。
- Subject Memory 可靠性证据：Summary source dispatch 先按真实 Agent/Project identity 唤醒对应 scope；scope worker 失败会持久化 defer，stale claim 可恢复，仍有待处理 Summary/Memory 时自动 rearm；每个 scope 通过独立 `subject_memory_scope_keys` 消费同一 Summary。
- 输出参数证据：Summary、Rollup、Agent Memory、Project Summary pipeline 已完全删除旧 `target_summary_tokens/target_tokens` 及其 `max_output_tokens` 传参；输入分批仍严格使用配置中心 `token_limit`。
- 配置刷新证据：Memory Engine 使用 `ConfigClient` 加载带 revision/checksum 的 snapshot，并每 30 秒 refresh；刷新失败只保留 last-known-good snapshot，不产生新的硬编码策略。
- 测试证据：在全新隔离 PostgreSQL 数据库完整应用迁移 0001–0007 后，Memory Engine PostgreSQL/单元测试 35/35、130/130；新增三条数据库契约测试覆盖配置阈值、Summary 同时产生 Rollup/Subject dispatch、Agent+Project typed scope 以及稳定 Agent Thread 的动态项目路由。配置中心 47/47，Memory SDK 39/39。

### ME-10 删除 Rust Responses 主动压缩的 `64000` 硬编码

- 状态：已完成
- 问题：`crates/chatos_ai_runtime/src/runtime.rs` 仍有 `ACTIVE_CONTEXT_COMPACTION_INPUT_TOKENS = 64_000`，每次官方 Responses 请求都会无条件传入该值；它与 Configuration Center 的 `agent.runtime.context_window_tokens`、实际模型上下文窗口和输出预留没有关联。
- 验收：先核对 OpenAI 官方 Responses compaction 参数语义以及本产品实际支持的主流模型窗口；再让压缩阈值来自唯一、可解释的配置/模型能力链路，或删除不应由客户端推断的传参。不得用另一个拍脑袋常量替换 `64000`。
- 参数语义：`context_management.compaction` 是长时间 Responses 工具循环的服务端主动压缩能力，不是 Memory Engine 的 Summary 输出长度；因此保留该能力，但只在模型使用 Responses 且快照明确携带阈值时发送。旧的 `ACTIVE_CONTEXT_COMPACTION_INPUT_TOKENS` 已删除。
- 唯一配置链路：Configuration Center 的 `agent.runtime.context_window_tokens` 与 `agent.runtime.output_reserve_tokens` → macOS 计算 `window - reserve` → 不可变模型配置快照及 revision hash → SQLite schema v45 → Rust Host `ModelRuntimeConfig` → Responses `context_management[0].compact_threshold`。恢复已有 Run 时继续使用原快照，不会因配置刷新改变中途请求策略。
- 数值依据（核对日期 2026-11-05）：Anthropic 官方完整文档明确仍受支持的 Claude Haiku 4.5 为 200K context，当前 Claude 新模型为 1M；DeepSeek 官方 Models & Pricing 页面当前模型为 1M context。OpenAI 官方文档从当前部署网络返回 403，未把无法读取的页面作为证据。产品默认安全窗口因此从无依据的 2M 调整为已核实下界 200K，输出预留沿用既有配置 30K，默认压缩点由公式得到 170K；生产仍以 Configuration Center 生效值为准。
- 代码证据：Rust、Swift 和本地快照生产路径已无 `ACTIVE_CONTEXT_COMPACTION_INPUT_TOKENS`；`ModelRuntimeConfig`、Local Agent snapshot、Agent Worker transport 与 Swift Responses client 均支持显式可选阈值；不支持或未配置时不发送 `context_management`。
- 测试证据：受影响 Rust packages `cargo check` 通过；`chatos_client_storage` 236/236、`chatos_ai_runtime` 264/264、`chatos_local_agent_host` 157/157、`chatos_agent` 17/17；Configuration Center 47/47；Swift Agent Runtime 相关筛选测试 76/76，Connector DTO/Team/Memory 相关测试通过；`git diff --check` 通过。
