# ChatOS 3.0.4 原生客户端重构与 Windows 对齐实施方案

状态：**待评审，未授权进入实现阶段**

分支：`3.0.4`

基线提交：`7e9b62a78`（已推送至 `origin/3.0.3`，`origin/3.0.4` 从该提交创建）

编制日期：2026-09-18

## 1. 目标与边界

本轮工作的目标是降低 macOS 与 Windows 原生客户端的结构复杂度，修复有证据支持的性能或设计问题，并补齐 Windows 相对 macOS 的产品能力。实施顺序固定为：

1. 锁定现有业务行为和持久化兼容性；
2. 完成 macOS 大文件拆分、抽象收敛和有基准支持的性能修复；
3. 完成 macOS 全量自动化与登录后关键路径测试；
4. 重新建立 Windows 能力差异基线；
5. 补齐 Windows 高优先级缺口并拆分对应大文件；
6. 在 Windows 环境至少完成全解决方案编译通过。

本轮不得改变以下业务语义：

- 云端仍是账号、对话和任务业务数据的权威来源；本机项目与设备能力仍由原生客户端授权和执行。
- Agent 的账号、项目、会话、团队、成员、Todo、消息、附件、Run 和 Memory scope 隔离规则不变。
- 项目经理权限、Todo 依赖、执行 lane、审批、恢复、取消、重试和终态规则不变。
- SQLite 已有数据必须原地升级且可继续读取；不得通过清库规避迁移问题。
- Local Connector、插件、终端、文件、Git、远端连接和安全边界不得放宽。
- UI 文案、默认值、排序、未读、焦点、滚动和错误恢复行为只有在回归用例明确覆盖后才能调整。

非目标：不借重构顺带改变产品交互，不迁移云端协议，不重写技术栈，不在没有基准的情况下做“感觉更快”的优化。

### 2.3 已发现的性能与设计候选问题

这些项目进入“测量后修复”队列，当前不直接断言为线上性能故障：

1. Agent 房间发生任意变更后，`AgentGroupChatViewModel` 延迟 120ms 再执行完整 `load()`；补充加载还会读取多类提案、Todo、资产、未完成 Run 和最近 500 个 Run。高频 Run 更新可能造成重复全量查询和 UI 刷新。
2. 图片附件通过消息和附件双层循环逐个跨 actor 查询，再逐个从磁盘读取，存在 N+1 I/O 和不可见图片提前解码的风险。
3. `SQLiteAgentGroupChatStore` 每次查询都重新 prepare/finalize statement；是否值得缓存语句必须通过真实热路径基准决定，不能先引入缓存生命周期复杂度。
4. `AppModel` 每 450ms 轮询 Visual Session，即使相关 UI 不可见也持续运行；优先评估事件流，否则采用可见性驱动与有界退避。
5. Agent heartbeat 最长每 60 秒查询一次并调用账号级 drain。保留到期唤醒语义，但需要确认空闲时没有无效写入、重复 drain 或唤醒风暴。
6. `AppModel` 同时承担依赖组装和多条运行时循环，生命周期与取消边界难以独立验证。
7. Agent Store、Tool Provider 与 Core 模型的单文件耦合会放大任何业务修改的评审面和回归风险。

性能改动必须满足：有稳定复现、有前后数据、有回归测试、无业务语义变化。没有数据支持的候选项只做结构拆分，不做行为优化。

### 2.4 Windows 与 macOS 的实际差距

现有 Windows 同步登记最后更新于 2026-08-31。此后 macOS 在 2026-09-16 至 2026-09-18 新增了 35 个与本地 Agent 相关的提交，约涉及 114 个 macOS 文件、33,682 行新增；Windows 源码中没有 Local Agent、Agent Group Chat、Agent Team、Agent Todo 或对应 Skill/Memory/Run 调度实现。

因此 Windows 当前缺口分两组：

**A. 新增的整条本地 Agent 垂直能力：**

- Agent Profile、职业、思考级别、权限和技能目录；
- 人与 Agent 私聊、Agent 间私聊、项目团队群聊和成员管理；
- Agent/团队/成员/项目创建与移除提案及人工审批；
- 项目经理管理的 Todo、依赖图、执行计划、进度、取消、阻塞和恢复；
- 团队资产、附件、消息分页、未读和稳定引用；
- 本地持久化、Schema 迁移、Run checkpoint、账号级 heartbeat 和崩溃恢复；
- Relay MCP 工具、能力发现、插件暴露、Durable Memory 和进程取消；
- Agent 管理、团队工作区、私聊、Todo、资产、Run inspector 和 Skill 管理 UI。

**B. 既有同步登记中的未完成项：**

- 删除失效模型时清理 Windows 本地审批模型 ID；
- Raycast 风格全局快速搜索；
- 本地剪贴板历史；
- 原生屏幕录制；
- Network Guard 的 WDK/微软生产签名和真机证据（该项不以普通编译通过代替正式安全验收）。

Windows 现有“大文件”问题较 Mac 轻，但插件 OAuth、Manifest、安装器、AppContainer、项目运行、主窗口和聊天 ViewModel 已达到 800–1,053 行。移植 Agent 能力时不得继续堆入这些文件，应沿 Core / API / Connector / Presentation / Desktop 分层新增独立模块。

## 3. 实施阶段

### 阶段 0：行为冻结与可测基线

1. 为所有待拆文件建立职责清单、公共 API 快照和依赖图。
2. 补齐缺失的 characterization tests，优先覆盖：
   - SQLite 从历史 Schema 到当前 Schema 的逐版本升级；
   - 消息、未读、附件、提案、Todo 依赖、Delivery 和 Run 的事务原子性；
   - scheduler 并发、公平性、取消、崩溃恢复和 exactly-once claim；
   - Tool Provider 的权限拒绝、引用隔离、参数解码和响应 JSON；
   - ViewModel 的选择保持、分页、滚动、错误恢复和重复事件合并。
3. 建立可重复的性能场景：空账号、20 Agent/10 团队、500 消息、500 Run、100 Todo、含图片附件页面。
4. 记录启动、房间首次加载、增量消息、Run 高频更新、空闲 CPU、数据库请求数和主线程长任务基线。

退出条件：基线测试全绿，性能脚本可重复，任何重构前都能检测业务语义漂移。

### 阶段 1：macOS Core 与持久化纯拆分

建议文件布局：

```text
ChatOSCore/AgentGroupChat/
  LocalAgentProfile.swift
  LocalAgentProposal.swift
  AgentConversation.swift
  AgentTodo.swift
  AgentTeamAsset.swift
  AgentRun.swift
  AgentGroupChatStore.swift
  AgentGroupChatValidation.swift

ChatOSConnector/AgentGroupChatStore/
  SQLiteAgentGroupChatStore.swift        # actor facade
  AgentGroupChatDatabase.swift           # connection/query/transaction primitives
  AgentGroupChatSchema.swift
  AgentGroupChatMigrations.swift
  AgentProfileRepository.swift
  AgentConversationRepository.swift
  AgentProposalRepository.swift
  AgentTodoRepository.swift
  AgentTeamAssetRepository.swift
  AgentRunRepository.swift
  AgentGroupChatRowMapper.swift
```

要求：

- 第一轮只移动代码和收窄依赖，不改 SQL、索引、排序、事务边界、错误文本或 Codable 字段。
- facade 继续满足原协议，调用方不感知内部拆分。
- 不通过把大量 `private` 改成全局 `internal` 来完成拆分；数据库原语由最小内部类型封装。
- 每个拆分提交运行 Store、Core 和完整 `swift test`。

退出条件：原有数据库文件可升级和读取；全部快照一致；生产文件职责清晰且无循环依赖。

### 阶段 2：macOS Tool Provider、Scheduler 与运行时拆分

1. 将 `LocalAgentChatToolProvider` 拆为工具注册、引用授权和领域工具组；工具名称、JSON Schema、错误码和响应字段保持逐字兼容。
2. 将 Scheduler 拆为账号租约、工作 claim、Run 组装执行、恢复和失败策略；保留每账号串行、不同账号可并行以及 manager/executor lane 约束。
3. 将 Durable Memory、插件工具提供者和进程取消边界显式注入，消除从 UI 组合根隐式获取依赖。
4. 为所有 Task 增加明确所有者、取消路径和结束断言；不允许 detached fire-and-forget 逃逸账号生命周期。

退出条件：调度压力测试、取消/恢复测试和 Tool JSON golden tests 全绿；无新增非结构化共享状态。

### 阶段 3：macOS UI 与组合根拆分

1. 将 Agent 团队页按 Chat、Todo、Assets、Runs、Members 拆分，Sheet 独立文件化。
2. 将 Workspace ViewModel 从 SwiftUI View 文件移出，并把房间主快照与补充数据加载建模为可取消的 generation。
3. 将 `AppModel` 收敛为组合根和顶层导航状态；提取：
   - `VisualSessionCoordinator`；
   - `AgentHeartbeatCoordinator`；
   - `WorkspaceRefreshCoordinator`；
   - `AuthenticationSessionCoordinator`；
   - `ConversationViewModelCache`。
4. 拆分 Story Studio 与 Media Studio 的状态、生成编排和展示组件。

退出条件：UI 状态回归测试全绿；主窗口、宠物、Visual Session、Agent 工作区和媒体工作区生命周期可独立测试。

### 阶段 4：macOS 有数据支持的性能与设计修复

按收益和风险排序：

1. 将房间变更刷新改为 coalesced snapshot 或增量刷新，避免同一批事件重复完整 `load()`。
2. 附件元数据批量读取，图片按可见区域懒加载，并使用有上限的内存缓存。
3. Visual Session 优先切换为事件驱动；无法事件化时，仅在相关会话活跃时高频刷新，后台有界退避。
4. 对真实热点 SQL 使用 `EXPLAIN QUERY PLAN`；只在证明缺索引或 prepare 成本显著时增加索引或 statement cache。
5. 将 heartbeat 的下一到期时间和 drain 触发解耦，确保空闲账号不会产生持续写入。
6. 检查主线程文件 I/O、Markdown 渲染、图片解码和超大数组排序，把可安全后台化的工作移出 MainActor。

验收标准：

- 所有业务测试继续通过；
- 相同数据集没有查询次数或主线程耗时回退；
- 任何声称的性能改善至少在 3 次重复测量中稳定出现；
- 新缓存均有容量上限、失效规则和内存压力行为；
- 不用延长 debounce、吞事件或降低数据新鲜度换取表面性能。

### 阶段 5：macOS 整体验收

自动化门禁：

```bash

swift test --package-path clients/macos
make test-macos-client
clients/macos/scripts/package-debug-app.sh
```

测试账号仅通过运行时 Secret 或环境变量注入。禁止写入 Markdown、源码、测试 fixture、shell history、CI 日志或 Git；失败截图和日志必须检查并遮蔽账号标识、Token、消息正文和本机路径。

退出条件：自动化全绿，打包 App 可启动，关键路径通过，性能报告和未解决风险归档。

### 阶段 6：Windows 差异重建与实现

1. 以 `2a3acc318..3.0.4` 的 macOS 变更为输入重建同步登记，不再沿用“基本对齐”的旧结论。
2. 先移植平台无关语义：Core 模型、校验、Store contract、调度状态机和 Tool contract。
3. 再实现 Windows SQLite repository、Memory/Plugin/Process adapter 和账号生命周期协调器。
4. 再实现 Presentation 与 WinUI：Agent 管理、私聊、团队、Todo、资产、Run 和 Skill 管理。
5. 处理既有 CP-20260831-001 至 004；快速搜索、剪贴板和录屏使用 Windows 原生 API，不照搬 macOS 实现。
6. 同步拆分 Windows 现有热点：
   - `PluginOAuthBroker`：store、discovery、authorization、token lifecycle；
   - `PluginManifestLoader`：manifest decode、runtime resolution、launch validation；
   - `WindowsPluginPackageInstaller`：download/verify/extract/install/rollback；
   - `WindowsAppContainerSandbox`：profile、ACL、launch、lease/cleanup；
   - 主窗口、聊天和项目运行 ViewModel：导航状态与领域状态分离。

Windows 首轮正式完成条件按用户要求设为“编译通过”，但实现过程中仍运行可用单元测试，避免用删除测试或排除代码换取绿色构建。

## 4. 提交、评审与回滚策略

- 所有工作只在 `3.0.4` 分支进行。
- 一个提交只包含一个可解释的拆分或修复；纯移动与行为修改不得混在同一提交。
- 每个提交保留可编译状态；自动化失败不得推送为阶段完成点。
- 数据库迁移提交必须附旧库 fixture、升级测试和失败回滚说明。
- 每阶段结束推送远端并更新本文的完成清单、测量数据和剩余风险。
- 发现业务语义无法由现有测试判定时暂停该小项，列出选择给用户评审，不自行改产品规则。

## 5. 定时任务执行协议

评审通过后，绑定当前 Codex 任务的 heartbeat 每 30 分钟运行一次，每次只推进一个有界工作单元：

1. 拉取并确认 `3.0.4` 工作区干净且未被其他提交改写；
2. 读取本文的当前阶段和最近一次验证结果；
3. 选择一个可在本轮完成、验证和回滚的最小改动；
4. 实现并运行最小测试，再运行阶段门禁；
5. 测试通过后提交并推送 `3.0.4`；
6. 只要本轮实际修改了仓库，就在 `docs/progress/3.0.4/` 新建一份不可覆盖的时间戳进度文件，记录目标、起始提交、实际改动、涉及文件、业务不变量、验证结果、代码提交、剩余风险和下一步；
7. 代码改动与进度记录分开提交，进度记录必须引用本轮代码提交哈希；没有仓库改动时不创建空进度文件，也不得修改历史记录；
8. 仅在阶段完成、发现性能/设计问题、验证失败或需要用户决策时通知；无实质变化时保持安静；
9. Mac 阶段 5 未完成前不得开始 Windows 功能移植。

停止条件：需要产品语义选择、遇到连续无法复现的环境故障、发现可能破坏用户数据的迁移风险，或 Windows 真机/签名等外部条件缺失。
