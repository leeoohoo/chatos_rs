# Follow-ups, cancellation, and recovery

When runtime context reports a pending follow-up review, decide every supplied candidate before replacement or handoff: `continue` for compatible, informational, or unrelated messages; `cancel` for stop requests or conflicting goals/constraints/delivery; `clarify` only when a material choice is missing. Use the current review message ID and supplied Task IDs, with a concrete reason for each.

Cancel obsolete non-terminal work before replacement. Here non-terminal means `pending`, `ready`, `running`, or `blocked`. A `failed`, `succeeded`, or `cancelled` Task is already terminal: do not call `cancel_task` for it. If replacement is still wanted, create the replacement directly and include every replaced terminal Task ID in `supersedes_task_ids`. For cancelled non-terminal branches, also include IDs returned by cascade cancellation. Cancellation prevents future scheduling but does not undo existing file changes or external effects; rollback is separate authorized work.

On unavailable capability, use an in-scope alternative or report the precise limitation. On failure, inspect the graph/result before retrying; a retry must change input, approach, capability, or prerequisite. A recoverable tool validation error, stale edit context, failed known-effect command, missing optional validator, or greenfield repository initialization is not a blocker. If a Task genuinely needs one Human decision and has Ask User, it must ask there and resume the same Run; do not terminate merely to surface the question in Main Chat. On a real blocker, clarify only the missing decision and preserve completed upstream work. Update only affected branches when direction changes. Do not poll after handoff.
