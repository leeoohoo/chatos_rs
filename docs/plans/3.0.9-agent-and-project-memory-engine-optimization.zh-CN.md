# 3.0.9 Agent 与 Project Memory Engine 整体优化方案

> 状态：3.0.9.6 一次性交付方案
>
> 日期：2026-11-04
>
> 适用范围：Main Chat、普通 Agent 会话、Agent Team、Todo 执行、审批 Agent
>
> 核心原则：每个 Agent 使用自己的固定 ID 和长期会话 Thread；Task/Todo 使用独立 Thread；长期记忆只归 Agent；项目只维护项目级总结；`room_id` 不参与 Memory 归属。

## 1. 结论

当前系统“每一个任务一个 Thread”本身没有问题。问题在于，普通会话没有稳定归入当前 Agent 唯一的长期会话 Thread，Task Thread 也没有稳定汇聚到执行 Agent Memory 与当前 Project Summary；因此审批 Agent、Todo 和 Agent Team 即使留下了聊天记录，后续运行也很难真正利用这些记录。

本次优化不合并原始聊天记录，也不把一个 Agent 的所有任务强行写进同一个长期 Thread。最终模型如下：

```text
Agent 长期会话 Thread：client-agent:agent:<agent_id>
Task/Todo 独立 Thread：client-agent:todo:<todo_id> 或 task:<task_id>
    ├── 全部汇聚到 Agent Memory：agent:<agent_id>
    └── 有项目时汇聚到 Project Summary：project:<project_id>

每次模型运行输入：
    当前 Thread 上下文
    + 当前执行 Agent 自己的记忆
    + 当前 Project 的最近总结（有项目时）
```

其中：

- 每个 Agent 都有独立、固定的 `agent_id`；`jiguli` 只代表叽咕狸，其他内置 Agent、用户创建 Agent 和 Agent Team 成员都使用自己的 ID，绝不回退或归并到 `jiguli`。
- 同一个 Agent 的普通会话（包括跨项目会话）写入同一个 Agent Thread；Task/Todo 仍各自使用独立 Thread，但摘要归入执行 Agent。
- `project_id` 不是 Agent 身份，只是跨 Agent、跨 Task 的项目事实总结范围。
- `room_id`、`delivery_id`、`todo_id` 只保留为来源追踪和审计元数据，不创建 Room Memory，不参与召回范围选择。
- Team 只是 Agent 工作的交互界面，不创建 Team Memory。
- Thread 仍然是原始事实和审计边界；Agent Memory 与 Project Summary 都是从 Thread/Record Summary 二次归纳出来的派生信息。

## 2. 目标与非目标

### 2.1 目标

1. 同一个 Agent 的普通会话统一进入自己的稳定 Thread，独立 Task Thread 也能形成连续的 Agent Memory。
2. 同一个 Project 内，不同 Agent、不同 Task 的有效结论可以形成 Project Summary。
3. 每一次 Agent 模型调用都自动获得自己的记忆；有项目时还自动获得当前项目的总结。
4. Main Chat、普通 Agent、Agent Team、Todo 和审批 Agent 使用同一套身份与聚合规则。
5. 主要逻辑放在 Memory Engine，ChatOS 只负责提供经过校验的身份和生命周期信号。
6. 保持原始 Thread 隔离、权限边界、工具调用审计和恢复能力。

### 2.2 非目标

- 不把所有原始 Thread 物理合并成一段聊天记录。
- 不创建 `room:<room_id>`、`team:<room_id>` 或其他 Room/Team 记忆主体。
- 不允许模型通过工具参数自行选择任意 `agent_id`、`project_id` 或 Memory subject。
- 不使用摘要代替当前任务目标、授权、审批、工具结果或数据库中的权威状态。
- 不让 Project Summary 变成所有 Agent 私有对话的全文共享区。

## 3. 当前实现诊断

### 3.1 已有能力

Memory Engine 已经具备本方案需要的大部分底层能力：

- Thread Summary 与 Subject Memory 两层摘要；
- 按 `source_thread_label` 聚合多个 Thread Summary；
- `subject_memory_scope_keys` 可让同一份 Thread Summary 分别被 Agent scope 和 Project scope 消费；
- Subject Memory scope、分层 rollup、事件队列和 Outbox；
- `related_subject_ids` 和 Agent label 识别；
- tenant/source/thread 的基础隔离。

因此本次不需要重写摘要引擎，重点是统一身份契约、自动注册聚合 scope、区分 Agent/Project 提示词，并扩展 compose 返回多个有类型的记忆块。

### 3.2 主要问题

1. `clients/local_agent_host/layers/profiles/src/memory.rs` 的身份曾从 `profile_key` 推测，可能把不同 Agent 错归到同一个伪 Agent。
2. `crates/chatos_ai_runtime/src/memory_context/record_writer.rs` 的通用写入路径仍可能用 tenant 作为 `subject_id`，无法表达真正的记忆所有者。
3. Swift `AgentMemoryScope` 的 manager、Todo、story、approval 曾使用不同策略，未统一遵守“Agent 固定 ID + 普通会话稳定 Thread + Task 独立 Thread”的契约。
4. `memory_engine/backend/src/services/context/blocks.rs` 虽然能收集多个 subject id，但最终固定只返回一条 Subject Memory，Agent Memory 与 Project Summary 会互相抢占。
5. Subject Memory 的默认提示词更偏用户画像/人格记忆，不能直接承担项目状态总结。
6. 独立 Task 往往达不到 token 压缩阈值；Task 结束后若不主动 flush，Thread 内容不会及时进入 Agent/Project 聚合。普通会话和审批会话则应继续累积，到阈值后再摘要，不能每次请求都摘要。
7. Team、Todo、审批和 Main Chat 尚未完全使用同一套身份契约。

### 3.3 根因

当前实现把以下三个概念混在了一起：

| 概念 | 正确职责 | 当前风险 |
| --- | --- | --- |
| Thread | 保存一次独立会话/任务的原始记录和审计 | 被误当作长期记忆身份 |
| Agent | 拥有跨 Thread 的长期经验和连续性 | 身份没有在所有入口稳定传递 |
| Project | 汇总项目共享事实、状态与决策 | 与 room、story subject 或单 Thread 绑定混杂 |

优化的关键不是减少 Thread 数量，而是把 Thread 与长期 Memory subject 正确解耦。

## 4. 最终身份模型

### 4.1 Thread Identity

Thread 分为两类：

- Agent 长期会话 Thread：`client-agent:agent:<agent_id>`。同一用户下同一 Agent 的 Main Chat、项目会话、普通会话和审批交互都持续写入这一条 Thread。
- Task/Todo 独立 Thread：每一个实际执行任务单独建立 Thread，重试同一任务时可复用；任务结束后摘要汇入执行 Agent 和记忆项目。

建议 Thread 类型：

- `main_chat`
- `agent_conversation`
- `agent_team_run`
- `todo_execution`
- `approval_agent`
- `story_agent`

新的 Task/Todo 创建新 Thread；新的普通对话或审批请求不创建新的 Agent Thread。跨项目时 Agent Thread 不变，当前 `project_id` 随 Record/compose 请求传递。

### 4.2 Agent Identity

稳定 Agent subject：

```text
agent:<canonical_agent_id>
```

要求：

- `canonical_agent_id` 由程序确定并校验，不能来自模型参数。
- tenant 隔离继续生效，因此 subject 字符串不需要包含用户 ID。
- 叽咕狸使用固定 ID `agent:jiguli`；`main_chat` 只是运行 profile，不是 Agent，也不得生成 `agent:main-chat`。
- 其他内置 Agent、Agent Team 中创建的 Agent 和用户 Agent 都使用各自固定 ID，与叽咕狸同级，不能归到 `agent:jiguli`。
- 审批 Agent 使用固定 ID，例如 `agent:local_connector_command_approval_agent`，不能把每次审批的 `runID` 当 Agent 身份。
- Todo 的执行 Agent 是 Todo 的受让 Agent；Todo 自己不是长期记忆所有者。

Agent Memory 可以跨该 Agent 所参与的多个项目保持连续，因为它代表的是该 Agent 自己的经验、偏好、能力、已知约束和未完成承诺；任何运行都只能读取当前执行 Agent 自己的 Agent Memory。

### 4.3 Project Identity

稳定 Project subject：

```text
project:<canonical_project_id>
```

Project Summary 汇聚同一项目内多个 Agent、多个 Thread 的可共享事实，但不拥有 Agent 私有原始记录。其内容限于：

- 已确认目标、范围和约束；
- 架构与产品决策及理由；
- 当前进度、已完成工作和下一步；
- 关键文件、接口、数据结构和环境事实；
- 未解决问题、风险和阻塞；
- 对后续项目工作可复用的结论。

不得写入：

- 与项目无关的 Agent 私人记忆；
- 原始私聊全文；
- 凭证、密钥、敏感工具输出；
- 未确认的猜测；
- 能被误认为当前授权的历史审批结论。

### 4.4 Provenance，不是 Memory Scope

以下字段继续保存，但只用于追踪、审计、排障和幂等：

```text
room_id
team_id
todo_id
delivery_id
run_id
message_id
```

它们不得：

- 生成独立 Subject Memory；
- 决定 compose 召回哪个长期记忆；
- 改变 Agent 身份；
- 因为一次 room 唤醒而限制 Agent 只能看到该 room 的记忆。

## 5. 统一运行行为

| 入口 | 原始 Thread | Agent Memory | Project Summary | 说明 |
| --- | --- | --- | --- | --- |
| 叽咕狸 Main Chat/项目会话 | `client-agent:agent:jiguli` | `agent:jiguli` | 绑定项目时注入 | `main_chat` 只是 profile |
| 普通 Agent 会话 | `client-agent:agent:<agent_id>` | 当前 Agent | 绑定项目时注入 | 同 Agent 跨项目连续 |
| Agent Team 普通沟通 | `client-agent:agent:<agent_id>` | 实际执行 Agent | 当前团队所处 Project | 不创建 Team/Room Memory |
| Todo 执行 | Todo 独立，重试可复用 | Todo 受让 Agent | Todo 所属 Project | 原始历史不并入 manager Thread |
| 审批 Agent | `client-agent:agent:local_connector_command_approval_agent` | 固定审批 Agent | 当前请求所属 Project | 多次审批累积到阈值再摘要 |
| Story/其他项目 Agent | 自己的稳定 Agent Thread | 实际执行 Agent | 当前 Project | 不再只靠 project subject 代替 Agent 记忆 |

所有入口在模型运行前都遵循同一上下文顺序：

```text
1. 系统规则与当前授权边界
2. 当前任务/当前 Thread 的权威目标
3. 当前 Thread Summary
4. 当前 Agent 的高层 Memory + 最近增量
5. 当前 Project 的高层 Summary + 最近更新（若有）
6. 当前 Thread 的近期原始记录
7. 当前未闭合工具调用及结果
```

系统规则、当前授权和当前数据库状态始终高于历史记忆。Memory 内容必须以“历史背景/可能过期的信息”注入，模型不得用它覆盖当前输入。

## 6. 数据契约

### 6.1 ChatOS 写给 Memory Engine 的最小身份

每次创建或确保 Thread 时至少提供：

```json
{
  "thread_id": "独立且稳定的 Thread ID",
  "subject_id": "agent:<canonical_agent_id>",
  "labels": [
    "memory-schema:v2",
    "agent:<canonical_agent_id>",
    "thread-kind:<kind>"
  ],
  "metadata": {
    "agent_id": "<canonical_agent_id>",
    "project_id": "<canonical_project_id or null>",
    "room_id": "<provenance only>",
    "todo_id": "<provenance only>",
    "delivery_id": "<provenance only>",
    "run_id": "<provenance only>"
  }
}
```

`subject_id` 统一采用 Agent subject。Agent 长期会话 Thread 会跨项目，因此不把某一个项目永久写进 Thread label；每条 Record 通过 `metadata.memory_project_id` 标明当次所属项目，compose 通过当前 `project_id` 读取对应 Project Summary。Task/Todo Thread 只属于一个项目时，可以同时写入 `project:<canonical_project_id>` label。

### 6.2 身份信任边界

- Agent/Project ID 来自 ChatOS 已验证的运行记录、Agent 配置和项目关系。
- Agent Team 使用 scheduler/runtime scope 中已有的 `agent_id`、`project_id`，不从 room 名称或消息文本推导。
- Todo 使用任务板中已确认的 assignee 和 project。
- 客户端必须从已绑定会话或 Agent 配置明确传入真实 Agent ID；叽咕狸 Main Chat 和项目会话传 `jiguli`，切换到其他 Agent 就传该 Agent 的真实 ID。
- Host 和 Memory Engine 只校验、使用显式身份；缺少或冲突时直接报错，不根据 `profile_key`、标题、UUID、room 或历史 metadata 猜测。
- approval 使用固定审批 Agent ID和当前请求所属 project。
- compose 请求中的 subject 只能与 Thread 注册身份一致；不接受任意覆盖。
- labels 更新必须防止已创建 Thread 被改绑到另一个 Agent 或 Project；需要迁移时走受控管理流程并留下审计。

## 7. Memory Engine 改造

### 7.1 自动注册 Agent 与 Project 聚合 scope

Memory Engine 在 Thread 创建/更新时识别保留 label：

- `agent:<agent_id>`：幂等确保 Agent Memory scope；
- `project:<project_id>`：幂等确保 Project Summary scope；
- `thread-kind:<kind>`：仅用于策略和观测。

建议 scope：

| scope | subject_id | memory_type | source_thread_label |
| --- | --- | --- | --- |
| Agent | `agent:<agent_id>` | `agent_memory` | `agent:<agent_id>` |
| Project | `project:<project_id>` | `project_summary` | `project:<project_id>` |

同一 Thread 同时带 Agent 和 Project label，其 Thread Summary 可以被两个 scope 独立消费。现有 `subject_memory_scope_keys` 已能记录每个 scope 的消费状态，不需要复制原始 Thread。

自动注册应放在 Memory Engine，而不是让每个 ChatOS 调用方手工调用控制面接口。这样 Main Chat、Native Agent、Rust Host、Team scheduler 和审批路径只需遵守一份 Thread 身份契约。

### 7.2 区分两类摘要提示词

不能继续让 Agent Memory 和 Project Summary 共用一套用户画像式提示词。

Agent Memory 提示词应提取：

- Agent 已掌握的稳定知识和工作方式；
- 已作出的重要判断及经验；
- 与用户协作中的稳定偏好；
- 该 Agent 需要继续履行的承诺；
- 可跨 Thread 复用、但不会冒充当前事实的信息。

Project Summary 提示词应提取：

- 项目目标、现状、决策、产物、接口和风险；
- 多 Agent 之间需要共享的项目事实；
- 结论的来源 Thread、时间和置信度；
- 已过期或被替代结论的状态。

Project prompt 必须显式要求删除私密对话细节、凭证、无关人格信息和历史审批授权含义。

### 7.3 Compose 返回多块记忆

移除当前 `FIXED_SUBJECT_MEMORY_LIMIT = 1` 所造成的单条竞争。不要简单把 limit 改大后混合返回，而应按 subject 和 memory type 分组、限额和排序。

目标返回：

```text
thread_summary_top_level
thread_summary_level0
agent_memory_rollup
agent_memory_recent
project_summary_rollup
project_summary_recent
recent_records
```

每个长期 subject 至少返回：

- 一条最高层 rollup，提供稳定全貌；
- 若干尚未进入 rollup 的最近 level-0 增量，提供时效性。

顺序必须确定，块类型必须明确，不能让客户端解析自由格式文本来猜测它属于 Agent 还是 Project。Compose 元数据增加每类命中数量、token 估算和截断原因。

### 7.4 由 Thread 身份解析召回范围

Memory Engine 根据已注册 Thread 的权威 `subject_id`/labels 解析 Agent subject，并根据当前已验证的 Record/compose 项目身份解析 Project subject。`related_subject_ids` 必须满足：

- 只接受 Thread 已绑定的 Agent/Project subject；
- tenant/source 必须一致；
- 请求额外 subject 时不一致则返回错误，不静默扩大范围；
- 模型工具层永远不可直接控制该字段。

### 7.5 Task 及时进入长期记忆

保留现有 token 阈值触发，同时增加两种触发：

1. **Task terminal flush**：独立 Task/Todo 完成、阻塞或取消时，异步确保最后一段记录生成 Thread Summary。
2. **Task/Todo idle flush**：独立 Task/Todo Thread 有新增记录但一段时间无活动时，由 Memory Engine 的延迟队列生成增量摘要，作为 terminal flush 失败或未到达终态时的兜底。

普通 Agent 会话和审批 Agent 不在每次请求结束时 terminal flush；它们持续写入稳定 Agent Thread，达到正常摘要阈值后自动摘要。ChatOS 最多只为独立 Task 发送 Thread lifecycle 状态或一个幂等的 terminal hint；摘要调度、去重、重试和失败恢复由 Memory Engine 负责。

### 7.6 一致性与幂等

- Thread Summary 先落库，再通过 Outbox 唤醒 Agent/Project scope。
- Agent 和 Project scope 分别记录消费游标。
- 同一 summary 对同一 scope 最多消费一次；失败可重试。
- 新增 level-0 后先提供 recent delta，后台再生成高层 rollup。
- rollup 生成失败时保留旧 rollup和新 delta，不能返回空记忆。
- 原始记录、Thread Summary、Agent Memory、Project Summary 均保留来源 ID 和时间。

## 8. ChatOS 最小改动

### 8.1 统一 MemoryIdentity

在公共 runtime 定义一份程序内部结构，Swift 与 Rust 字段一致：

```text
MemoryIdentity
  tenant_id
  source_id
  thread_id
  agent_id
  project_id?
  thread_kind
  provenance { room_id?, todo_id?, delivery_id?, run_id? }
```

所有入口在创建 Runtime 时一次性生成并冻结。Memory writer、compose 和 lifecycle flush 都消费该对象，避免各模块自行拼 ID。

### 8.2 Local Agent Host / Main Chat

- `memory_plan` 除 Thread scope 外，写入稳定 Agent ID、可选 Project ID 和 thread kind。
- Main Chat 使用 `jiguli`，而不是 tenant、profile key 或 conversation ID 作为 Agent subject。
- 叽咕狸的 Main Chat 和项目会话统一写入 `client-agent:agent:jiguli`；UI conversation ID 只保留为来源元数据。
- 新 Task 从 Main Chat 派生时显式传递执行 Agent 和 Project；不继承 room 作为 scope。

### 8.3 Native Agent 与 Agent Team

- `AgentMemoryScope` 以真实 `agent_id` 建立该 Agent 唯一的长期会话 Thread。
- manager、团队唤醒和普通沟通复用实际 Agent Thread；Task/Todo 才使用独立 Thread。
- scheduler 和 Native Team Executor 统一使用已有 `agent_id + project_id`；`team_id/room_id/delivery_id` 只进入 provenance。
- Agent A 的执行记录进入 Agent A Memory；Agent B 的执行记录进入 Agent B Memory；两者通过 Project Summary 共享项目事实。

### 8.4 Todo

保留 `client-agent:todo:<todo-id>` 的独立原始 Thread 和重试连续性，但改变两点：

1. compose 时读取受让 Agent Memory 和当前 Project Summary；
2. Todo Thread Summary 同时贡献给受让 Agent scope 和 Project scope。

这不会把 Todo 原始记录塞进 Agent manager Thread，也不会让 Todo 读取其他 Todo 的原始历史。它只通过摘要形成该 Agent 自己的长期经验和项目共享结论。

### 8.5 审批 Agent

审批 Agent 与普通 Agent 一样拥有稳定会话 Thread：

- 所有审批记录写入 `client-agent:agent:local_connector_command_approval_agent`；
- 有 Project 时同时绑定 `project:<project_id>`；
- 允许读取审批 Agent 自己的历史 Memory 和当前 Project Summary；
- 删除当前“一律关闭 Subject Memory”的长期策略，改为安全类型的历史召回；
- 系统提示必须声明：历史批准/拒绝仅为参考，当前请求必须依据当前路径、命令、参数、权限和用户授权重新判断；
- 历史 Memory 永远不能自动批准当前操作；
- 单次审批结束不强制摘要，累计达到阈值时再摘要。

### 8.6 通用 Record Writer

修正用 `tenant_id` 充当 `subject_id` 的默认行为。没有显式、已验证 Agent Identity 时直接拒绝 Memory 运行。不得根据 profile、标题、room、UUID 或历史 metadata 回退到叽咕狸，也不得继续把租户本身当作一个巨大的记忆主体。

## 9. Agent Team 的具体边界

Team 场景必须遵守以下不变量：

1. 消息属于实际发送/执行它的 Agent，而不是 room。
2. Team 中的每个任务仍有自己的 Thread。
3. Team 协作产生的稳定项目结论进入 Project Summary。
4. Agent 私有推理、无关历史和未公开内容不能因为同处一个 Team 自动进入 Project Summary。
5. room 关闭、重建、改名或 delivery 重试，不改变 Agent Memory 和 Project Summary 身份。
6. Agent 离开 Team 不删除其自己的 Memory；项目访问权限变化后，后续 compose 不再向无权运行注入该 Project Summary。

## 10. 安全、权限与数据隔离

### 10.1 读取规则

一次运行最多读取：

- 当前 tenant/source/thread；
- 当前执行 Agent 自己的 `agent:*`；
- 当前已授权 Project 的 `project:*`。

不能读取其他 Agent Memory，也不能仅凭已知 ID 读取其他 Project Summary。

### 10.2 写入规则

- Thread 创建后绑定 Agent 不可由普通调用任意修改。
- Project label 必须通过 ChatOS 权限校验。
- Memory Engine 校验 subject 与 Thread labels 的一致性。
- Project Summary 的生成器只能消费带同一 project label 的 Thread Summary。
- 删除/归档项目时，Project Summary 按项目保留策略处理；Agent Memory 中的来源引用仍需遵守数据删除要求。

### 10.3 记忆不是授权

下列内容始终不能只从 Memory 恢复：

- 当前审批结论；
- 当前工具执行许可；
- 付费操作确认；
- 凭证和密钥；
- 当前文件/数据库的权威状态；
- 幂等键、锁、任务版本和未完成工具调用状态。

## 11. 历史数据策略

本版本不做兼容层、别名、猜测迁移或自动回填：

- 新请求必须明确携带真实 `agent_id`，并写入 v2 权威身份。
- 不从 `profile_key`、会话标题、UUID、`room_id`、旧 metadata 或旧 Thread 前缀推断 Agent。
- 旧数据可以继续留在数据库中，但不自动归入任何新 Agent Memory，也不影响新身份目录。
- 若上线前决定不要旧数据，应单独执行明确、可审计的数据清理；本实现不擅自删除或迁移。
- 不重放历史工具、不改变历史审批结果。

## 12. 可观测性

至少增加以下指标和日志字段：

- `thread_identity_bound_total{thread_kind}`
- `thread_identity_missing_total{entrypoint}`
- `agent_scope_registered_total`
- `project_scope_registered_total`
- `thread_summary_terminal_flush_total{status}`
- `thread_summary_idle_flush_total{status}`
- `subject_scope_pending_summaries{memory_type}`
- `subject_memory_rollup_lag_seconds{memory_type}`
- `compose_blocks_returned{block_type}`
- `compose_identity_mismatch_total`
- `project_summary_redaction_total{reason}`
- 每次 compose 记录 thread、agent subject、project subject、块数量和截断原因，但不记录正文和敏感内容。

管理侧应能查看：某个 Thread 绑定了哪个 Agent/Project、其摘要是否已被两个 scope 消费、最后一次 rollup 时间和失败原因。

## 13. 一次性交付范围

3.0.9.6 不保留双写、中间态或兼容分支，以下内容完成后一起上线：

- 客户端在所有入口明确传递真实 `agent_id` 和当前 `project_id`。
- Rust Host、Swift Agent Runtime 和通用 Record Writer 统一使用同一身份规则。
- 普通会话使用 Agent 稳定 Thread，Task/Todo 使用独立 Thread。
- Memory Engine 自动维护 Agent Memory 与 Project Summary，并按类型 compose。
- 管理侧按 Agent → 项目 → Thread 展示，只读取 v2 权威身份。
- Task terminal flush 与普通会话 threshold/idle 摘要策略同时生效。
- 身份矩阵、隔离、PostgreSQL 契约、macOS 客户端与真实 Host 链路全部通过后，提交、推送、服务端发布并重装 macOS 客户端验证。

## 14. 验收标准

### 14.1 功能验收

- [ ] 同一 Agent 连续执行两个独立 Task，第二个 Task 能召回第一个 Task 的 Agent Memory，但看不到第一个 Task 的原始全文。
- [ ] 同一 Project 中 Agent A 的有效项目结论进入 Project Summary，Agent B 后续运行可召回该结论。
- [ ] Agent B 不能读取 Agent A 的私有 Agent Memory。
- [ ] Todo 保持独立 Thread，同时能读取受让 Agent Memory 和 Project Summary。
- [ ] Todo 完成后，其有效结论能分别更新受让 Agent Memory 与 Project Summary。
- [ ] 同一用户的所有审批记录写入审批 Agent 的稳定 Thread，并按累计阈值摘要。
- [ ] 历史审批中的“允许”不能导致新审批自动通过。
- [ ] Team room 改名/重建后，Agent 与 Project Memory 连续性不受影响。
- [ ] 叽咕狸在 Main Chat、项目会话和由它创建的 Task 中始终使用 `agent:jiguli`。
- [ ] 其他 Agent 的会话和 Task 始终使用自己的 ID，不会归到 `jiguli`。
- [ ] 独立 Task 结束后无需达到 token 阈值，也能在限定时间内进入聚合；普通会话和审批不会每次强制摘要。

### 14.2 隔离验收

- [ ] 任意传入其他 `related_subject_ids` 会被拒绝。
- [ ] tenant/source/project 权限不匹配时 compose 失败且不泄露存在性。
- [ ] `room_id` 不会生成 Subject Memory scope。
- [ ] Project Summary 不包含凭证、原始私聊全文或无关 Agent 人格信息。
- [ ] 删除或撤销项目访问后，后续运行不再注入该 Project Summary。

### 14.3 可靠性验收

- [ ] 重复 terminal flush、Outbox 重试和 worker 重启不会重复消费摘要。
- [ ] Project rollup 失败时，旧 rollup 与最近 delta 仍可召回。
- [ ] compose 输出顺序稳定，token 预算分别限制 Agent/Project/Thread。
- [ ] 不启用历史身份猜测、别名或兼容回填，也不重放工具或修改历史审批状态。

## 15. 对旧约定的修订

本方案保留 `docs/3.0.8-agent-communication-and-todo-runtime.zh-CN.md` 中以下原则：

- room/project 不是 Agent 运行身份；
- room 不决定 Memory；
- Todo 原始执行历史与沟通层原始历史隔离；
- delivery、room、todo 等标识可以保留作审计。

但明确修订其中“Todo 不继承 Agent 沟通层 Memory”的表述：

- Todo **不继承或合并 Agent manager 的原始 Thread**；
- Todo **必须召回受让 Agent 的聚合 Memory**；
- Todo **必须召回当前 Project Summary**；
- Todo 产生的有效摘要应反向贡献给受让 Agent Memory 和 Project Summary。

审批 Agent 改为稳定 Agent Thread，召回自己的 Agent Memory 与当前 Project Summary，并把历史明确标记为非授权背景；单次审批结束不强制摘要。

## 16. 最终不变量

实现完成后，系统必须始终满足：

1. 每个任务可以是独立 Thread。
2. 每个 Agent 有且只有一个固定 ID；`jiguli` 只属于叽咕狸，其他 Agent 永远不归到 `jiguli`。
3. 每个 Agent 的普通会话使用自己的稳定 Thread；Task/Todo 使用独立 Thread，但归入执行 Agent Memory。
4. 每个 Project 只有项目事实总结，不拥有 Agent 私有原始聊天。
5. 每次 Agent 运行都带自己的 Agent Memory；有项目时再带当前 Project Summary。
6. Agent Team、Todo、Main Chat 和 approval 不得绕过这套规则。
7. `room_id` 永远只是来源信息，不是 Memory scope。
8. 身份缺失或冲突时直接失败，不做兼容、别名或猜测。
9. 记忆提供连续性，但不提供当前授权，也不替代权威状态。
